# 音视频流媒体协议

> 音视频编解码第6课 — 从RTMP到WebRTC

## 流媒体传输核心

### 实时vs点播

| 特性 | 实时流 | 点播流 |
|------|--------|--------|
| 延迟要求 | < 500ms | 无严格要求 |
| 缓冲策略 | 最小缓冲 | 大缓冲保流畅 |
| 常用协议 | WebRTC/RTMP | HLS/DASH |
| 适用场景 | 直播/会议 | 视频平台/录播 |

### 核心指标
- **延迟**：从采集到显示的时间差
- **首屏时间**：用户点击到第一个画面
- **卡顿率**：播放过程中缓冲等待的百分比
- **自适应码率**：根据网络动态切换品质

## RTMP (Real-Time Messaging Protocol)

### 特点
- Adobe 私有协议，TCP 长连接
- 推流主流，播放逐渐被淘汰
- 低延迟（2-5秒）
- 基于FLV封装格式

### 协议栈
```
视频编码(H.264) → 封装(FLV) → RTMP(TCP) → 服务器 → CDN → 播放端
音频编码(AAC)  → 封装(FLV) → RTMP(TCP) → 服务器 → CDN → 播放端
```

### 消息类型
1. **命令消息**（AMF编码）：connect/createStream/publish/play
2. **音频数据**：原始AAC数据包
3. **视频数据**：原始H.264 NAL单元
4. **用户控制消息**：流开始/结束/缓冲区长度

### 局限性
- 播放端Flash已死（Adobe 2020停止支持）
- 纯TCP，不支持HTTP/2多路复用
- 端口 1935 常被防火墙拦截
- 无原生自适应码率

## HLS (HTTP Live Streaming)

### 原理
Apple 提出的基于 HTTP 的分片流媒体协议。

```
推流 → 编码器 → 切片器 → TS/fMP4文件
                     ↓
                    M3U8播放列表
                     ↓
                 HTTP/HTTPS分发
                     ↓
                  CDN缓存
                     ↓
                 播放器拉流
```

### 工作流程
1. **切片**：将实时流切成2-10秒的TS/fMP4文件
2. **生成播放列表**（M3U8）：列出所有可用分片
3. **自适应码率**（Master Playlist）：多码率版本
4. **播放器**：逐片下载、拼接、解码、渲染

### M3U8 结构
```m3u8
#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=1280000,RESOLUTION=1280x720
medium.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=2560000,RESOLUTION=1920x1080
high.m3u8
```

### 延迟优化
- **普通HLS**：6~30秒（3分片×片长）
- **LL-HLS (Low-Latency)**：2~5秒
  - 更短的分片（0.2~1秒）
  - 部分分片（Partial Segments）
  - 抢先下载（Preload Hint）
  - 阻塞播放列表刷新（Blocking Playlist Reload）

## DASH (Dynamic Adaptive Streaming over HTTP)

### 特点
- MPEG国际标准，开源、免专利费
- 基于HTTP/2多路复用
- 支持多种编码和封装（fMP4/WebM）

### 与HLS对比
| 特性 | HLS | DASH |
|------|-----|------|
| 标准 | Apple私有 → RFC | MPEG国际标准 |
| 封装 | TS/fMP4 | fMP4/WebM |
| 编码 | H.264为主 | 任意编码 |
| 加密 | FairPlay | Widevine/PlayReady |
| 可用性 | iOS原生支持 | 需播放器SDK |
| 延迟 | 6-30s (LL:2-5s) | 6-30s (LL:2-5s) |

## WebRTC (Web Real-Time Communication)

### 架构
```
Peer A ──── STUN/TURN ──── Peer B
   │          ↗ ↖            │
   │    ┌────┘   └────┐      │
   │    │  信令服务器  │      │
   │    └─────────────┘      │
   │                        │
   └─── SRTP/SCTP ──────────┘
```

### 核心组件
1. **媒体引擎**：VP8/VP9/H.264编解码器，Opus音频编解码
2. **传输层**：ICE/STUN/TURN NAT穿透，DTLS加密，SRTP媒体加密
3. **信令**：SDP Offer/Answer，WebSocket/HTTP信令通道
4. **数据通道**：SCTP协议传输任意二进制数据

### 延迟表现
| 类型 | 典型延迟 | 适用 |
|------|---------|------|
| 一对一通话 | 50-200ms | 视频会议 |
| 多人MCU | 100-500ms | 多人会议（服务端混流） |
| 直播SFU | 200-1000ms | 万人直播（转发型） |

### 自适应码率（GCC）
WebRTC 内置的Google Congestion Control算法：
- 基于丢包的策略：丢包率>2%时降低码率
- 基于延迟的策略：RTT增加说明网络拥塞
- 最终码率 = min(接收端预估带宽, 发送端预估带宽)

## 自适应码率（ABR）算法

### 常见策略
| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 基于吞吐量 | 前一分片下载速度 | 简单易实现 | 波动敏感 |
| 基于缓冲区 | 缓存量决策升/降级 | 防卡顿 | 反应慢 |
| 混合型 | 吞吐量+缓存+预测 | 综合最优 | 实现复杂 |
| 基于强化学习 | 训练RL模型决策 | 长期最优 | 需要训练数据 |

### 实用ABR策略（混合型）
```
if(缓存 > 10秒) → 尝试升级码率
if(缓存 < 3秒)  → 立即降级码率
if(吞吐量 > 码率×1.5) → 准备升级
if(吞吐量 < 码率×0.8) → 准备降级
```

## CDN与边缘计算

### 流媒体CDN的关键
1. **边缘缓存**：热点内容缓存到离用户最近的节点
2. **预取策略**：预测用户下一个分片提前拉取
3. **回源优化**：多级缓存减少源站压力
4. **区域调度**：DNS/GSLB解析到最优节点

### 新兴趋势
- **LL-ABR**（低延迟自适应）：「分片越小，选择越快」
- **CMAFFragmented MP4**：支持字节级范围请求，延迟降至1-2秒
- **AV1 + DASH**：开源生态的完美组合

## 总结
- RTMP用于推流，HLS/DASH用于分发，WebRTC用于实时交互
- ABR算法从简单吞吐量到混合RL在持续进化
- LL-HLS + WebRTC 是低延迟直播的两大方向
- CDN边缘计算是规模化分发的基石
