# 分布式一致性：CAP定理与共识算法

> 日期：2026-05-07 19:34 | 课程：DB路线 Phase 3-1
> 目标：理解"多台机器怎么保持一致"

## 核心问题

```
一台MySQL → 单点故障，容量有限
三台MySQL → 数据怎么同步？网络断了怎么办？
```

## CAP定理

```
C = Consistency (一致性) — 所有节点数据一样
A = Availability (可用性)  — 请求都能得到响应
P = Partition Tolerance (分区容忍性) — 网络断了还能工作

定理: C、A、P 三者只能选两个
```

### 但关键是——P 必须选

```
分布式系统里，网络中断（分区）是必然发生的
所以实际是在: CP 和 AP 之间选

CP (银行/转账): 
  网络分区时→阻塞写入→保证一致性
AP (社交/Feed): 
  网络分区时→接受不一致→保证可用
```

### 实际例子

| 系统 | 选择 | 为什么 |
|------|------|--------|
| MySQL主从 | CP | 同步复制，从库可能延迟 |
| Redis集群 | AP | 最终一致性，先响应再说 |
| Zookeeper/Etcd | CP | 配置中心，一致性优先级高 |
| Cassandra | AP | P2P架构，写可分区 |

## Paxos — 共识算法

### 思想
> **"一半以上的人同意 = 决定"**

```python
# 一个简单的问题：
# 3个节点要决定"余额是多少"
# 不能出现：A说100，B说200，C说100

# Paxos解法：
# 1. 提案者(Proposer)发起"我提议余额=100"
# 2. 接受者(Acceptor)投票
# 3. 半数以上同意 → 决定生效

# 关键保证：
# 最多只有一个值被选中
# 选中的值对所有人可见
```

## Raft — Paxos的简化版

```
Paxos出了名的难理解（论文很多人看不懂）
Raft把共识拆成三个角色，更容易理解
```

### Raft的三个角色

| 角色 | 职责 |
|------|------|
| Leader | 处理一切写请求，协调日志复制 |
| Follower | 被动接收Leader的日志 |
| Candidate | 选举时的临时角色 |

### Raft的关键机制

```
1. Leader选举
   如果Follower一段时间收不到Leader心跳
   → 变成Candidate → 发起选举 → 获票过半 → 成为新Leader

2. 日志复制
   所有写请求走Leader
   Leader复制到多数Follower → 才认为"提交"
   
3. 安全性
   一个Term（任期）只有一个Leader
   日志只在Leader之间单向流动（不会乱）
```

## 今日收获
- CAP: C和A只能保一个，P必须保
- **共识 = 一半以上同意 = 决定**
- Paxos难懂但数学严谨，Raft易懂且生产可用
- Etcd/Consul 都用 Raft（配置中心/K8s的核心）
- 理解CAP = 理解分布式系统的设计约束
