# 存储引擎 #2：B+Tree vs LSM-Tree 深度对比

> 2026-05-17
> 前置：LSM-Tree 原理 #1

## 1. 架构对比

### 1.1 B+Tree 的核心特征

```
磁盘页（4KB-16KB）为单位的树结构：
- 内部节点：维护键值指针，不存数据
- 叶子节点：存实际数据，形成双向链表

写入路径：
  Put(key, value)
    ↓
  1. 二分查找找应该插入的叶子页
  2. 页内有空间 → 插入
  3. 页满了 → 分裂（Split），写放大 2x
    ↓
  写入到页缓存 → 后台异步刷盘（Checkpoint）
  写入 WAL 确保持久性
```

### 1.2 LSM-Tree 的核心特征

```
分层文件结构 + 内存缓冲区：

写入路径：
  Put(key, value)
    ↓
  1. 追加到 WAL（顺序写）
  2. 写入 MemTable（内存跳表）
  3. MemTable 满 → flush 为 SSTable（顺序写）
  4. 后台合并（Compaction）
```

## 2. 读写性能对比

### 2.1 随机写入

| 操作 | B+Tree (InnoDB) | LSM-Tree (RocksDB) | 差异 |
|------|----------------|-------------------|------|
| 1KB 随机写入 | ~500 条/秒 | ~15,000 条/秒 | **30x** |
| 4KB 批量随机写入 | ~3 MB/s | ~50 MB/s | **16x** |
| 单个 key 插入 | 页缓存命中 ≈ 10μs，未命中 ≈ 5ms | 内存写入 ≈ 0.5μs | **100x** |

**LSM-Tree 胜出原因**：
- B+Tree 每写一条数据可能触发页分裂（随机写）
- LSM-Tree 总是顺序写 WAL + 内存写入

### 2.2 顺序扫描

| 操作 | B+Tree (InnoDB) | LSM-Tree (RocksDB) |
|------|----------------|-------------------|
| 单点查询 (PK) | ~1μs (缓存命中) | ~1μs (MemTable) ~10μs (SST, Bloom 不命中跳过) |
| 范围查询 | ✅ 单向链表遍历，快 | ✅ SST 内有序，但合并排序开销大 |
| 小范围 100条 | ~5μs | ~20μs |
| 大范围 10000条 | ~500μs | ~2000μs |

**B+Tree 胜出原因**：
- 叶子节点链表直接遍历，没有多余的合并排序

### 2.3 随机读取

B+Tree 在随机读取上通常也略快：
- LSM-Tree 的读放大（要检查多层级）
- Bloom Filter 减少了很多无效检查，但仍比 B+Tree 多

## 3. 性能权衡全景

### 3.1 三大放大因子

| 因子 | B+Tree | LSM-Tree (LevelDB) | LSM-Tree (RocksDB tuned) |
|------|--------|-------------------|--------------------------|
| 写放大 | 2-4x | 10-40x | 3-10x |
| 读放大 | 3-4x | 10-30x | 2-5x（+ Bloom Filter） |
| 空间放大 | 1.1x | 1.3-2x | 1.1-1.5x |

### 3.2 场景选择决策

```
需要高写入吞吐？（日志、时序、消息队列）
  → LSM-Tree（RocksDB / LevelDB / Cassandra）

需要低延迟点查？（在线交易、用户数据）
  → B+Tree（MySQL / InnoDB）

需要大批量扫描？（数据分析、报表）
  → B+Tree（定向索引扫描）或 ColumnStore

混合负载（读写均衡）？
  → RocksDB（调优 Compaction + Bloom Filter）
    或 B+Tree（足够大的 Buffer Pool）
```

## 4. 实战选型：存储引擎对比

| 引擎 | 底层结构 | 写入 | 单点读 | 范围扫描 | 典型场景 |
|------|---------|------|--------|---------|---------|
| InnoDB | B+Tree | ❌ | ✅✅ | ✅✅ | OLTP |
| MyRocks | LSM-Tree | ✅✅ | ❌ | ❌ | 写入密集型（日志/时序）|
| WiredTiger | B+Tree + LSM | ✅ | ✅ | ✅ | MongoDB（混合）|
| LevelDB | LSM-Tree | ✅ | ❌ | ❌ | 嵌入式 |
| RocksDB | LSM-Tree ✅✅ | ❌ | ❌ | ❌ | KV 存储、流处理 |
| Cassandra | LSM-Tree ✅ | ❌ | ❌ | ✅ | 宽表、时序 |
| Redis | 哈希 | ✅✅ | ✅✅ | ❌ | 纯内存缓存 |

## 5. 量化系统中的应用

当前量化引擎的数据需求分析：

| 数据 | 写入模式 | 查询模式 | 引擎 |
|------|---------|---------|------|
| 实时行情 tick | 高频追加 | 最近 N 条 | RocksDB |
| K 线数据 | 定期追加 | 历史范围扫描 | Parquet / ClickHouse |
| 交易日志 | 高频追加 | 按日期范围 | RocksDB |
| 策略参数 | 低频更新 | 点查 | 内存 KV |
| 回测结果 | 批写入 | 聚合查询 | SQLite |

**最匹配的存储引擎场景**：实时行情和交易日志的写入大量 > 读取，LSM-Tree 天然适合。

## 总结

```
选 B+Tree 当：
  ✅ 单点读取是最关键路径
  ✅ 有大量范围扫描
  ✅ 写入吞吐不是瓶颈

选 LSM-Tree 当：
  ✅ 写入吞吐 > 读取吞吐
  ✅ 追加为主（日志、时序）
  ✅ 能接受偶尔的合并抖动

最佳实践：两者结合
  热数据 → LSM-Tree（高写入）
  冷数据 → B+Tree（高效读取）
  数据流化：Presto/Trino 统一查询
```
