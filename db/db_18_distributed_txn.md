# 分布式事务：从 2PC 到 Seata AT

## 2PC / 3PC

### 两阶段提交 (2PC)
- **Phase 1 (Prepare)**: 协调者问所有参与者"能提交吗？"；参与者写 undo/redo log 后回复 Yes/No
- **Phase 2 (Commit/Abort)**: 全 Yes 则 Commit，任一 No 则 Abort
- **致命问题**: 协调者单点；Phase 2 中协调者宕机则参与者阻塞(同步阻塞)；没有容错机制

### 三阶段提交 (3PC)
- 引入 **CanCommit** 预询阶段(超时可提前 abort) + **PreCommit** + **DoCommit**
- 加入超时机制，参与者超时后自动 Commit(降低阻塞)
- **问题**: 仍可能不一致(网络分区下参与者检测不到协调者 abort 而自动 commit)

## TCC (Try-Confirm-Cancel)

- **Try**: 资源预留(冻结库存、锁定余额)
- **Confirm**: 真正执行(扣减库存、转账)
- **Cancel**: 回滚释放(释放预留)
- **优点**: 无锁、高性能、2 阶段网络开销小
- **缺点**: 业务侵入大，每个操作都需要 Try/Confirm/Cancel 三接口
- **适用**: 短事务、高并发、对一致性要求"最终一致"即可

## SAGA

- 长事务拆分为多个本地事务 + 补偿事务
- **编排模式 (Orchestration)**: 中心协调器按顺序调用子事务
- ** choreography ( choreography )**: 每个服务完成后发送事件触发下一步
- 补偿是业务级回滚(逆向操作)，不是数据库回滚

## 本地消息表

- 本地事务中写业务表 + 消息表(同库事务保证)
- 异步扫描消息表发送到 MQ，消费方幂等处理
- **经典案例**: 支付宝跨行转账(本地事务写流水 + 消息表，MQ 通知银行网关)
- **优点**: 简单可靠；**缺点**: 消息表耦合业务库，需自行清理

## Seata AT 模式

- **核心思想**: 自动生成反向 SQL 做回滚(对业务透明)
- **流程**: TM 开启全局 TX → RM 执行 SQL 前记录 before image → 执行 SQL → 记录 after image → 生成 undo log
- **两阶段**: Phase 1 提交本地事务 + 注册分支；Phase 2 全局提交删除 undo log/回滚用 undo log 恢复
- **写隔离**: 全局锁 (GlobalLock) 保证写冲突检测；读未提交 + 本地锁保证行级隔离
- **性能**: 比 2PC 好，但全局锁是瓶颈

## XA vs BASE 取舍

| 维度 | XA (DTP 模型) | BASE 柔性事务 |
|------|---------------|---------------|
| 一致性 | 强一致 | 最终一致 |
| 性能 | 差(锁时间长) | 好 |
| 吞吐 | 低 | 高 |
| 适用 | 短小、低并发 | 长事务、高并发 |
| 代表 | 2PC、TCC | SAGA、本地消息、Seata AT |

**结论**: 业务场景决定。金融核心用 XA 保强一致；互联网高并发用 BASE 柔性事务+补偿
