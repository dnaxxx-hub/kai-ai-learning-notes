# 事务与ACID：数据库的可靠性基石

> 日期：2026-05-07 19:29 | 课程：DB路线 Phase 1-2
> 目标：理解"多步操作要么全做要么全不做"

## 核心直觉

```
银行转账: A账户扣100元 → B账户加100元
中间系统崩溃 → A少了100，B没收到 = 灾难

事务的作用：保证这两步"原子化"——要么都执行，要么都没执行
```

## ACID

| 特性 | 含义 | 怎么实现 |
|------|------|---------|
| **A**tomicity 原子性 | 事务要么全执行，要么全不执行 | Undo Log |
| **C**onsistency 一致性 | 事务前后，数据约束都满足 | 应用层 + 数据库约束 |
| **I**solation 隔离性 | 并发事务互不干扰 | 锁 + MVCC |
| **D**urability 持久性 | 提交的事务永远不丢 | Redo Log + WAL |

## 逐层拆解

### A — 原子性（Undo Log）

```python
# 事务修改数据前，先记下旧值到 Undo Log
# 如果事务回滚: 用 Undo Log 恢复旧值
# 如果事务提交: Undo Log 可以被清理（但MVCC可能需要保留）
```

### D — 持久性（Redo Log + WAL）

```python
# WAL (Write-Ahead Logging):
# 修改数据前，先写日志
# 日志写到磁盘后，事务才算"提交"
# 
# 这样就算数据页还没刷到磁盘就崩溃了：
# 重启时按 Redo Log 重放 → 数据恢复
```

### I — 隔离性（四种隔离级别）

## 事务的底层：WAL

```sql
-- 一条 UPDATE 背后发生了什么？
UPDATE users SET balance=900 WHERE id=1;

-- 1. 把 id=1 的数据页加载到 Buffer Pool（内存）
-- 2. 写 Redo Log（记录"把balance改成900"）
-- 3. 写 Undo Log（记录"balance原来是1000"）
-- 4. 在内存中修改数据页
-- 5. 用户返回成功

-- 6. 后台异步刷脏页到磁盘
-- 7. 如果不是立即commit，在commit时刷redo log到磁盘
```

## 一致性不是数据库能完全保证的

```python
# 数据库保证：
# - 约束（UNIQUE, FOREIGN KEY, NOT NULL）
# - 触发器等
# 
# 应用层保证：
# - 业务规则（"余额不能为负"——如果约束没设）
# - 引用完整性（"没有用户应该有负的年龄"）
#
# 一致性 = 数据库 + 应用代码一起保证
```

## 今日收获
- **ACID** = 数据库的可靠性承诺
- **Undo Log** 保证原子性（回滚时用）
- **Redo Log + WAL** 保证持久性（崩溃恢复）
- Buffer Pool = 数据库的"内存缓存层"
- 一致性需要应用和数据库共同努力
