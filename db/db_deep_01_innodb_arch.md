## InnoDB的存储层次

```
表空间(Tablespace) → 段(Segment) → 区(Extent) → 页(Page)
   .ibd文件         索引/BLOB等      1MB=64页       16KB默认
```

### 数据页（Page）

```python
# 数据库的最小读写单位（不是行！）
# InnoDB默认16KB（16384字节）

# 一个数据页的结构:
┌─────────────────────┐
│ File Header (38B)   │ ← 页号/上一页/下一页/校验和
├─────────────────────┤
│ Page Header (56B)   │ ← 页类型/记录数/空闲空间
├─────────────────────┤
│ Infimum + Supremum  │ ← 边界记录（虚拟行）
├─────────────────────┤
│ User Records        │ ← 真正的数据行（单向链表）
│ ...                 │
├─────────────────────┤
│ Free Space          │ ← 未使用的空间
├─────────────────────┤
│ Page Directory      │ ← 目录（二分查找入口）
├─────────────────────┤
│ File Trailer (8B)   │ ← 页完整性校验
└─────────────────────┘

# 关键: 页内的记录通过"Page Directory"实现二分查找
# 不是一行一行遍历的
```

### 区（Extent）

```python
# 64个连续的页 = 1个区 = 1MB
# 索引分配以区为单位（不是页）
# → 尽量保证物理连续性 → 减少随机IO

# 但是小表（<32页）用"碎片页"
# 不马上分配完整的区
```

## Buffer Pool

### 核心作用

```python
# 数据库的"内存缓存层"

# 读: 先从Buffer Pool找 → 找不到再读磁盘 → 缓存在内存
# 写: 先改Buffer Pool里的数据页 → 后台异步刷盘

# 原理: 内存比磁盘快10万倍
# 目标: 尽可能让"热数据留在内存"
```

### LRU算法的变体

```python
# 标准LRU的问题:
# 执行一次全表扫描 → 把所有热数据挤出Buffer Pool
# 热数据被冷数据污染了

# InnoDB的改进: "Midpoint Insertion Strategy"

# Buffer Pool分成两段:
# ┌──────────────────────┬──────────────────────┐
#     新子列表(热数据)         旧子列表(冷数据)
#     默认占 5/8              默认占 3/8

# 新读入的页 → 放入旧子列表头部
# 如果旧子列表的页被再次访问 → 移到新子列表头部
# 全表扫描: 数据只会进入旧子列表，很快被淘汰
# 热数据: 留在新子列表，不受全表扫描影响
```

### 预读（Read Ahead）

```python
# 预测"你接下来可能需要什么"

# 线性预读:
# 你读了page 1 → 连续读了page 2
# InnoDB推测: 你可能要page 3,4,5,6,7...
# → 提前从磁盘读到Buffer Pool

# 随机预读:
# 你读了page 1和page 100（同一区）
# 推测: 同区的其他页也可能需要
# → 提前读整个区

# 预读的好处: 减少等待IO的时间
# 预读的坏处: 浪费内存（猜错了）
```

## 今日收获
- 存储层次: 表空间 → 段 → 区(1MB) → 页(16KB)
- 数据页内用Page Directory实现二分查找
- Buffer Pool = 内存缓存（读/写都在内存操作）
- InnoDB的LRU不是标准LRU（分段保护热数据）
- 预读 = 提前加载你"可能"需要的数据
