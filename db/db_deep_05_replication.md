# 主从复制与GTID

> 日期：2026-05-07 22:30 | 课程：数据库深水区 Phase 3-1
> 目标：理解"MySQL怎么把数据复制到多台机器"

## 复制的核心

```python
# 一台MySQL不够用 → 多台

# 主库(Master/Primary): 处理写请求
# 从库(Slave/Replica): 处理读请求

# 复制 = 主库的修改 → 同步到从库
```

## 复制流程（传统方式）

```
1. 主库执行事务 → 写binlog
2. 从库IO线程 → 从主库拉binlog → 写入relay log
3. 从库SQL线程 → 从relay log读 → 重放

# 三个关键线程:
# 主库: Dump线程（发送binlog给从库）
# 从库: IO线程（接收binlog写入relay log）
# 从库: SQL线程（重放relay log）
```

## 复制方式

### 1. 异步复制（默认）

```python
# 主库提交 → 从库自己拉binlog
# 主库不等待从库确认

# 如果主库挂了 → 从库可能少几条数据
# 适用: 允许少量数据丢失的场景
# 性能: 最好（主库不受影响）
```

### 2. 半同步复制

```python
# 主库提交 → 等待至少一个从库确认收到 → 返回成功

# 如果主库挂了 → 至少有一个从库有最新数据
# 适用: 数据一致性要求较高的场景
# 性能: 略差（多一次网络往返）
```

### 3. 组复制（Group Replication）

```python
# MySQL的"共识复制"
# 类似Raft/Paxos的协议

# 节点之间投票决定事务是否提交
# 多数节点同意 → 事务提交

# 自动选主（主库挂了自动切换）
# 一致性更高
# 但性能比异步复制差
```

## GTID（全局事务标识符）

```python
# 传统复制的痛点:
# - 用binlog文件名+偏移量定位 → 切换主库很麻烦
# - 需要手动找"从哪里开始同步"

# GTID = server_uuid:transaction_id
# 每个事务有唯一的ID

# 好处:
# 1. 主从切换更简单（自动定位）
# 2. 可以判断从库是否已经执行了这个事务
# 3. 可以并行复制（基于GTID分到不同工作线程）
```

## 主从延迟

```python
# 从库总是"落后"主库
# 原因:
# - 从库可能慢（硬件差）
# - 网络延迟
# - 从库SQL线程单线程重放（旧版）
  
# 解决方案:
# 1. 并行复制 → 多线程重放（基于库/基于GTID）
# 2. 半同步复制 → 减少延迟窗口
# 3. 读写分离中间件 → 自动判断延迟

# 如果延迟严重:
# - 从库查询到旧数据
# - 解决方案: 关键查询走主库
```

## 脑裂（Split-Brain）

```python
# 两个节点都以为自己是"主"
# → 数据不一致

# 常见原因:
# 网络分区 → 主库和从库无法通信
# 自动切换后原主库恢复

# 防止脑裂:
# - 仲裁节点（多数派）
# - STONITH（Shoot The Other Node In The Head）
# - MySQL Router / ProxySQL 中间件
```

## 今日收获
- 复制三阶段: 主写binlog → 从拉relay log → 从重放
- 异步/半同步/组复制 = 性能到一致性的取舍
- GTID = 每个事务一个唯一ID → 简化主从切换
- 主从延迟 = 无法完全消除 → 关键查询走主库
- 脑裂 = 两个主脑 → 需要仲裁/强制关闭一方
