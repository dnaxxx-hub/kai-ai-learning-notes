## 一、并发控制的两种基本方式

### 1.1 悲观并发控制（PCC）
通过锁机制保证安全——认为冲突是常见的，所以先加锁再操作。

### 1.2 乐观并发控制（OCC）
假设冲突很少——先做修改，提交时检查冲突。

| 对比 | 悲观锁 | 乐观锁 |
|------|--------|--------|
| 冲突频繁 | ✅ 好 | ❌ 回滚多 |
| 冲突稀少 | ❌ 锁开销大 | ✅ 无锁开销 |
| 死锁风险 | 有 | 无 |

## 二、锁类型

### 2.1 模式与兼容性

| 锁模式 | 缩写 | 含义 | 兼容 |
|--------|------|------|------|
| 共享锁 | S | 读锁，不阻塞其他读 | S+S ✅ |
| 排他锁 | X | 写锁，阻塞一切 | X 不兼容任何其他锁 |
| 意向共享锁 | IS | 表级，表示下属行上有 S 锁 | IS+IS ✅ |
| 意向排他锁 | IX | 表级，表示下属行上有 X 锁 | IX+IX ✅ |
| 共享意向排他锁 | SIX | 表级 S + 部分行 IX | 特殊 |

### 2.2 意向锁的作用

加速表级锁判断——不需要遍历所有行：
```
事务在 users 表的 row=42 上有 X 锁 → 在 users 表上设置 IX 锁
另一个事务请求 LOCK TABLES users WRITE → 看到 IX → 直接等待
```

## 三、行锁与间隙锁

### 3.1 Record Lock（行锁）
```
SELECT * FROM users WHERE id=42 FOR UPDATE;    -- X 锁
SELECT * FROM users WHERE id=42 LOCK IN SHARE MODE;  -- S 锁
```

### 3.2 Gap Lock（间隙锁）
锁住索引记录之间的"间隙"，防止幻读。

```
索引: [10, 20, 30, 40]
间隙: ( -∞, 10), (10, 20), (20, 30), (30, 40), (40, +∞)
```

`SELECT * FROM users WHERE age BETWEEN 25 AND 35 FOR UPDATE;`
→ 锁住所有匹配行 + 相邻间隙

### 3.3 Next-Key Lock
行锁 + 间隙锁的组合。MySQL InnoDB RR 级别默认使用：
```
锁定 (20, 30] — 前开后闭区间
```

## 四、两阶段锁（2PL）

### 规则
- **扩张期**：只能加锁，不能释放
- **收缩期**：只能释放，不能加锁
- 事务在第一个解锁操作后进入收缩期

### 严格2PL（SS2PL）
所有写锁在事务结束时才释放（用于实现级联回滚避免）

### 与 MVCC 的关系

| 场景 | 使用方式 |
|------|----------|
| 快照读（普通 SELECT） | MVCC 无锁 |
| 当前读（SELECT FOR UPDATE） | 2PL 加锁 |
| UPDATE/DELETE | 先 MVCC 检查，再加 X 锁 |

## 五、死锁

### 5.1 条件
1. **互斥**：资源只能一个事务用
2. **持有并等待**：持有一个锁，等待另一个
3. **不可剥夺**：锁不能强制解除
4. **环路等待**：T1→T2→T3→T1

### 5.2 检测
**等待图（Wait-For Graph）**：从节点到节点的有向边表示"等待"
```
T1 → T2  (T1 在等 T2 持有的锁)
T2 → T1  (T2 在等 T1 持有的锁)  ← 存在环 = 死锁
```

### 5.3 解决
1. **Victim 选择**：选最少修改 / 最年轻的事务回滚
2. **预防**：按固定顺序加锁（如按 PK 大小）
