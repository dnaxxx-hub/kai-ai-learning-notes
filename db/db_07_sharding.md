# 分库分表：单机放不下了怎么办

> 日期：2026-05-07 19:38 | 课程：DB路线 Phase 3-3
> 目标：理解"一张表放不下100亿条数据时怎么办"

## 核心问题

```
MySQL一张表超过500万行 → 性能开始下降
达到1亿行 → 索引层数增加，IO变多，查询变慢
达到10亿行 → 单机根本存不下

怎么办？——拆！
```

## 三种拆分方式

### 1. 分表（垂直拆分 - Vertical Partitioning）

```python
# 把表的列拆到不同的表
# 
# 原表: id, name, email, bio, avatar, created_at, login_count, ...
#
# 拆成:
# users_main:   id, name, email, created_at        （频繁查询的列）
# users_ext:    id, bio, avatar                     （低频/大字段）
# users_stats:  user_id, login_count, last_login    （统计字段）

# 好处: 每行变小 → 每页可以存更多行 → 查询更快
# 坏处: 查询需要多表JOIN
```

### 2. 分表（水平拆分 - Horizontal Sharding）

```python
# 把表的行拆到不同的表，结构一样
# 
# 根据分片键（Shard Key）决定去哪张表:

# 取模分片:      user_id % 4 → 路由到 4 张表之一
# 范围分片:      user_id 1-1000万 → 表1, 1000万-2000万 → 表2
# 哈希分片:      hash(user_id) % N

# 关键问题：分片键选错了 → 查询都要扫所有分片
```

### 3. 分库（Database Sharding）

```python
# 分到不同物理机器上（解决"一台机器存不下"的问题）
# 分库后 = 分布式系统了 → CAP问题来了

# 分库不能再跨库JOIN
# 不能跨库事务（除非用分布式事务，但性能差）
# 分页查询所有库再合并
```

## 分片键的选择

```sql
-- ❌ 坏选择：分片键 = 自增ID
-- 查询用户历史订单 → WHERE user_id=? → 不知道去哪张表
-- 必须扫所有分片

-- ✅ 好选择：分片键 = user_id
-- 同一个用户的所有数据在同一台机器
-- 查询该用户 → 直接路由到正确分片

-- 如果有跨分片查询需求：
-- 建立全局索引（ES或其他搜索引擎）
```

## 读写分离

```
主库(Master): 处理写请求（INSERT/UPDATE/DELETE）
从库(Slave):  处理读请求（SELECT）

优点:
- 写压力集中在一台（或少量主库）
- 读压力分散到多台从库
- 可以横向扩展（加从库）

缺点:
- 主从延迟（刚写完就读 → 可能读不到最新数据）
- 解决: 强制读主库（对实时性要求高的操作）
```

## 常见方案对比

| 方案 | 特点 | 代表 |
|------|------|------|
| 客户端分片 | 代码里决定路由 | ShardingSphere, MyCAT |
| 代理层分片 | 中间代理转发SQL | ProxySQL, Vitess |
| 原生分布式 | 底层自动分片 | TiDB, OceanBase, CockroachDB |

## 今日收获
- 垂直拆分 = 列拆分，水平拆分 = 行拆分
- **分片键的选择决定一切** → 选错了就是灾难
- 分库 = 解决了容量，带来了分布式问题
- 读写分离 = 水平扩展读能力
- TiDB等NewSQL = 自动分片 + 无需改代码
