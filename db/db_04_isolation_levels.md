# 隔离级别详解：何时需要什么级别

> 日期：2026-05-07 19:32 | 课程：DB路线 Phase 2-2

## 四种隔离级别的演进

### 1. READ UNCOMMITTED

```python
# "啥都不管，直接读最新的"
# 会读到未提交的数据（脏读）
#
# 实际应用：几乎没有
# 只有某些分析场景用（读个大概就行）
```

### 2. READ COMMITTED（RC）

```python
# "只读已提交的"
# 每个语句执行时获取新快照
# 防止脏读，但不防不可重复读

# 应用：PostgreSQL默认, Oracle默认
# 适合：读为主，写压力不大

# 问题：两次SELECT可能结果不同
```

### 3. REPEATABLE READ（RR）

```python
# "两次读同一行，结果一样"
# 事务开始时获取快照（事务ID）
# 之后所有读取都基于这个快照

# 应用：MySQL InnoDB默认
# 适合：需要一致性读的长事务

# 普通SELECT走MVCC快照读 → 无锁
# 但RR防幻读需要间隙锁(Next-Key Lock)
```

### 4. SERIALIZABLE

```python
# "所有事务串行化执行"
# 所有读都加锁（包括SELECT）
# 性能最差，但最安全

# 应用：要求严格一致性（银行转账核心）
```

## 间隙锁（Gap Lock）—— MySQL RR防幻读的关键

```sql
-- 表里有数据: id=1, 3, 5
-- 事务A:
SELECT * FROM users WHERE id BETWEEN 2 AND 4 FOR UPDATE;

-- 间隙锁锁的是"不存在的id区间"
-- 锁住: (1,3) 和 (3,5) 这两个间隙
-- 阻止其他事务插入 id=2 或 id=4

-- Next-Key Lock = 行锁 + 间隙锁

-- 如果事务A走的是索引，则锁对应索引的间隙
-- 如果没走索引 → 锁整个表
```

## 实际场景选择

| 场景 | 推荐隔离级别 | 原因 |
|------|------------|------|
| 报表分析 | RC | 不需要重复读，读最新即可 |
| 电商库存 | RR | 需要保证库存扣减一致性 |
| 社交Feed | RC | 读多写少，不需要严格隔离 |
| 银行转账 | SERIALIZABLE | 钱不能出错 |
| 日志写入 | READ UNCOMMITTED | 偶尔读错无所谓 |

## MySQL特殊情况

```python
# MySQL的RR并不可靠防幻读
# 只有在走唯一索引且查询命中时，才真正防幻读
# 普通索引/范围查询，RR仍可能出现幻读

# 所以有时候干脆用SERIALIZABLE或者应用层加锁
```

## 今日收获
- RC = 读已提交，RR = 可重复读（MySQL默认）
- RR用**间隙锁（Next-Key Lock）**防幻读
- 隔离级别越高 → 一致性越好 → 性能越差
- 不用C选项：SERIALIZABLE性能太差了
- 大部分应用选RC或RR
