# Change Buffer与自适应哈希索引

> 日期：2026-05-07 22:27 | 课程：数据库深水区 Phase 1-2
> 目标：理解"InnoDB还有两个隐形的加速器"

## 核心问题

```
普通索引（非唯一索引）的更新:
"UPDATE users SET age=18 WHERE name='张三'"

name上没有唯一约束 → 不在Buffer Pool里
→ InnoDB要先把name索引的数据页读到内存 → 修改
→ 但只是改一个值，不值得一次IO

Change Buffer: 先把修改"暂存"起来
等有空了再批量合并
```

## Change Buffer

### 工作原理

```python
# 用于: 非唯一辅助索引的修改（INSERT/UPDATE/DELETE）
# 不用于: 唯一索引（需要检查唯一性，必须读数据页）
# 不用于: 聚簇索引（主键索引）

# 流程:
# 1. 要改普通索引，数据页不在Buffer Pool
# 2. 不读磁盘 → 把修改记录到Change Buffer
# 3. 等数据页被读到Buffer Pool → 合并Change Buffer
# 4. 或者定期后台合并

# 好处:
# 减少了磁盘随机IO（改索引=随机写不同数据页）
# 把离散的随机写 → 合并成一次顺序写
```

### 什么时候有用

```python
# ✅ 高度适合:
# - 大量INSERT到非唯一索引（如日志表）
# - 索引列频繁修改
# - 大部分数据不在内存中

# ❌ 不太有用:
# - 唯一索引
# - 数据基本都在Buffer Pool里（直接改就行）
# - 写完马上读（需要合并 → 反而增加开销）

# innodb_change_buffer_max_size: 控制Change Buffer占Buffer Pool的比例
# 默认25%，可调到50%（写入密集型场景）
```

## 自适应哈希索引（AHI）

### 核心思路

```python
# 问题: B+树查找需要2~3次IO
# 纯内存的情况下 → 需要2~3次内存访问
# 但内存中的哈希表 → O(1)一次查找

# InnoDB自动判断:
# "如果这个索引页被频繁按等值条件访问"
# → 在内存中建一个哈希索引
```

### 工作机制

```python
# 条件:
# - 同一个索引页被访问超过N次（N=17次×页内记录数）
# - 访问模式是等值查询（=），而不是范围查询

# 哈希表结构:
# hash(key值) → 指向B+树中的具体记录

# 自适应:
# - 查询模式变了 → 自动重建/删除AHI
# - 不占用磁盘空间（只在内存）
# - 不需要DBA手动创建

# 监控:
# SHOW ENGINE INNODB STATUS\G
# → 查看"Hash table size"和"Heap size"等信息
```

### 什么时候生效

```python
# ✅ 适合:
# - OLTP系统（大量等值查询）
# - 热点数据集中在特定记录
# - 主键查找

# ❌ 不适合:
# - 全表扫描
# - 范围查询（> / < / BETWEEN）
# - 大表但没有热点
# - 数据仓库/分析型查询

# 但AHI也有代价:
# - 占用Buffer Pool内存
# - 有自旋锁竞争（高并发下）
# - 某些场景关闭AHI更快
```

## 为什么这两个特性重要

```python
# Change Buffer: 让你"写更快"
# AHI: 让你"读更快"
# 合起来: InnoDB在通用场景下的性能优化

# 它们都是"自适应"的:
# - 不需要配置（但可以调优）
# - 自动根据工作负载调整
# - 对大多数应用透明

# 这也是MySQL为什么"默认就好用"的原因之一
```

## 今日收获
- Change Buffer = 暂存非唯一索引的修改 → 减少随机IO
- 写入密集型场景可以调大 Change Buffer 比例
- AHI = InnoDB自动判断 + 内存哈希表 → O(1)查找
- AHI仅对"等值查询 + 热点数据"有效
- 两个特性都是"自适应的" —— InnoDB做了最好的选择
