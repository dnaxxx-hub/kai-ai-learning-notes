## 核心问题

**如何快速地在海量数据中找到一条记录？**

```
表里有1000万行，执行 SELECT * FROM users WHERE id=123456
数据库不可能一行行扫描——必须用索引
```

## B+树：数据库最通用的索引结构

### 结构示意

```
                [10, 20]            ← 内部节点（路由）
               /    |   \
         [1,3,5,7] [10-16] [20-36]  ← 叶子节点（实际数据/指针）
         ←→←→←→← 链表连接           ← 范围查询
```

### 关键特性

| 特性 | B+树 | 二叉树 | 哈希表 |
|------|------|--------|--------|
| 高度 | 2~4（百万级数据） | log₂N=20 | 1 |
| 范围查询 | ✅ O(logN + K) | ❌ | ❌ |
| 等值查询 | ✅ O(logN) | ✅ O(logN) | ✅ O(1) |
| 磁盘友好 | ✅ 每个节点=1个页 | ❌ 节点分散 | ❌ 哈希冲突 |

### B+树的三个核心设计

#### 1. 扇出（Fan-out）大
```python
# 一个数据页通常 16KB
# 一个索引条目 ~16B
# 所以一个内部节点可以存 ~1000个索引键

# 高度=3 → 1000 × 1000 × 1000 = 10亿条记录
# 只需要3次磁盘IO就能找到任何一行
```

#### 2. 叶子节点链表
```python
# 叶子节点之间用双向链表连接
# SELECT * FROM users WHERE id BETWEEN 100 AND 200
# 找到100 → 顺着链表遍历到200
# 性能远超哈希表
```

#### 3. 聚簇索引
```python
# InnoDB的聚簇索引: 叶子节点存的是整行数据
# 二级索引: 叶子节点存的是主键值 → 需要回表

# 所以主键设得好 = 减少一次回表
```

## B+树 vs LSM树

LSM树（LevelDB/RocksDB/TiDB的底层）：

```python
# 写入: B+树直接写数据页 → 随机IO
#        LSM先写内存(WAL) → 批量刷盘 → 顺序IO
#        
# 读取: B+树 3次IO找到 → 极快
#        LSM 需要检查多个SSTable → 慢一点
#
# 写入放大: B+树 中
#          LSM 高（compaction持续合并）
```

**B+树 = 读优化（MySQL）**
**LSM树 = 写优化（TiDB/RocksDB/Cassandra）**

    """概念演示——真正的B+树比这复杂10倍"""

## 今日收获
- 数据库的本质 = **磁盘太慢，内存太贵**
- B+树 = 用高度换IO次数（3层=10亿数据）
- 叶子链表 = 范围查询的杀手特性
- B+树读快写慢，LSM写快读慢
- 理解B+树 = 理解MySQL的InnoDB选型
