# 分布式事务：多节点的事务怎么保证

> 日期：2026-05-07 19:36 | 课程：DB路线 Phase 3-2
> 目标：理解"跨数据库的事务怎么搞"

## 核心问题

```
订单服务 → 扣库存（MySQL A）
订单服务 → 生成订单（MySQL B）
两者必须同时成功或失败——但MySQL A和B互相不知道对方
```

## 2PC（两阶段提交）

### 流程

```
第一阶段（准备阶段）:
  协调者 → 所有参与者: "准备好提交了吗？"
  参与者 → 协调者: "准备好了" / "我做不到"

第二阶段（提交阶段）:
  如果所有人都说准备好了:
    协调者 → 所有人: "提交！"
  如果有人说不:
    协调者 → 所有人: "回滚！"
```

### 问题

```python
# 1. 阻塞
#    参与者等协调者的最终指令，期间锁住资源
#    如果协调者挂了 → 参与者一直等 → 死锁

# 2. 单点故障
#    协调者崩了 → 整个事务卡住

# 3. 脑裂
#    第一阶段所有人都说"准备好了"
#    第二阶段协调者发"提交"——但网络断了
#    有人提交了，有人没收到指令 → 不一致
```

## 3PC（三阶段提交）

```
比2PC多了一个"预备提交"的阶段
减少阻塞时间，但没有完全解决问题
```

## TCC（尝试-确认-取消）

```python
# Try:    预留资源（冻结库存，冻结余额）
# Confirm: 确认执行（扣库存，转钱）
# Cancel:  取消回滚（解冻库存，解冻余额）

# 好处：没有长事务锁，性能好
# 坏处：业务侵入性强，每个操作都要实现Try/Confirm/Cancel
```

## 最终一致性（BASE）

```python
# Basically Available (基本可用)
# Soft State (软状态)
# Eventually Consistent (最终一致性)

# 思想：不要保证每一刻都一致
# 保证"最终会一致"
```

### 实现方式

```
1. 本地消息表
   订单表 + 本地消息表（同一MySQL）
   定时任务扫描消息表 → 发送到MQ → 库存服务消费

2. MQ事务消息
   RocketMQ支持半消息
   先发"半消息" → 业务执行 → 半消息变成"真消息"

3. Saga模式
   一系列本地事务
   每个事务有补偿操作（回滚）
   成功就往前走，失败就反向补偿
```

## 对比

| 方案 | 一致性 | 性能 | 复杂度 |
|------|--------|------|--------|
| 2PC | 强 | 差（阻塞） | 中 |
| TCC | 强 | 好 | 高 |
| 本地消息表 | 最终 | 好 | 低 |
| MQ事务 | 最终 | 好 | 中 |
| Saga | 最终 | 好 | 中 |

## 今日收获
- 2PC = 两阶段=准备+提交，有阻塞问题
- **分布式环境下强一致性很难**——这是CAP的限制
- 大部分实际系统用最终一致性 + 补偿机制
- TCC = Try/Confirm/Cancel，业务侵入强
- Saga = 每一步都有补偿，走不了就回滚
