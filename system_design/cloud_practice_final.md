## 1. 阿里云核心产品

### 1.1 ECS (Elastic Compute Service) 云服务器

| 概念 | 说明 |
|------|------|
| **实例** | 一台虚拟服务器，按规格（vCPU、内存）计费 |
| **镜像** | 操作系统模板（CentOS/Ubuntu/Windows/自定义） |
| **快照** | 磁盘的某一时间点副本，用于备份和恢复 |
| **弹性伸缩** | 根据负载自动增减实例数量 |

**使用模式：**
- 按量付费 vs 包年包月 — 短期弹性用按量，长期稳定用包年
- 实例规格族：通用型(g6/g7)、计算型(c6/c7)、内存型(r6/r7)
- 安全加固：绑定安全组 + 密钥对登录 + 云监控告警

### 1.2 OSS (Object Storage Service) 对象存储

- 存储任意类型文件（图片、视频、备份、日志）
- **Bucket**（存储空间）是基本容器，数据以 **Object**（对象）存储
- 存储类型：标准、低频访问、归档、冷归档
- 生命周期规则：自动将旧数据转入低频/归档
- CDN 加速：OSS + CDN 实现静态资源全球加速

### 1.3 RDS (Relational Database Service) 关系型数据库

- 支持 MySQL / PostgreSQL / SQL Server / MariaDB
- 自动备份、主备切换、读写分离
- **对比自建数据库**：免运维（补丁/备份/监控自动处理）
- 连接池、SQL 审计、慢查询分析

### 1.4 安全组 (Security Group)

- 虚拟防火墙，控制 ECS 实例的入方向和出方向流量
- **规则构成**：协议(TCP/UDP/ICMP)、端口范围、源IP/CIDR
- **最佳实践**：最小权限原则，仅开放必要端口
- 安全组是有状态的 — 出方向自动允许已建立连接的返回流量

### 1.5 SLB (Server Load Balancer) 负载均衡

- 将流量分发到多台 ECS 后端服务器
- 支持四层(TCP/UDP)和七层(HTTP/HTTPS)负载均衡
- 健康检查：自动移除异常后端、恢复后重新加入
- 调度算法：加权轮询(wrr)、最小连接数(wlc)、一致性哈希(sh)

### 1.6 VPC (Virtual Private Cloud) 专有网络

- 在云上创建一个隔离的、自定义的网络环境
- 子网划分 — 将 VPC 划分为多个网段
- 通过 NAT 网关 / VPN / 专线连接外部网络
- **核心概念**：VPC → 交换机(vSwitch) → 路由表 → 网关

## 2. AWS 核心产品（对照阿里云）

| 阿里云 | AWS | 功能对照 |
|--------|-----|----------|
| ECS | EC2 | 云服务器 — 概念几乎一致 |
| OSS | S3 | 对象存储 — Bucket/Object 概念相同 |
| RDS | RDS | 托管数据库 — 功能几乎一致 |
| 安全组 | Security Group | 虚拟防火墙 — 规则语法略有差异 |
| SLB | ELB (ALB/NLB) | 负载均衡 — 阿里云分类更简单 |
| VPC | VPC | 专有网络 — 概念完全一致 |

### 关键差异

| 维度 | 阿里云 | AWS |
|------|--------|-----|
| **可用区** | 地域(A) + 可用区(B/C) | Region + AZ (a/b/c) |
| **安全组规则** | 入方向和出方向分开配置 | 入站规则(inbound) + 出站规则(outbound) |
| **SLB vs ALB** | SLB 统一管理四层/七层 | ALB(HTTP/HTTPS) 和 NLB(TCP/UDP) 分开 |
| **计费粒度** | 秒级计费（部分实例） | 秒级计费（EC2 大部分实例） |
| **IAM** | RAM (Resource Access Management) | IAM — AWS 更成熟，细粒度更高 |

### 当从阿里云迁移到 AWS 时需要关注的差异

1. **IAM 权限模型** — AWS IAM 使用 Policy Document(JSON)，阿里云 RAM 使用策略名称绑定
2. **安全组规则表达** — AWS 支持引用其他安全组作为源，阿里云需指定 CIDR
3. **VPC 默认行为** — AWS 默认不创建 VPC，阿里云默认创建
4. **实例元数据获取** — 都通过 169.254.169.254 获取，但路径不同

## 3. 基础设施即代码 (IaC)

### 3.1 核心概念

```
声明式 (Declarative)          命令式 (Imperative)
  ┌─────────────┐               ┌─────────────┐
  │ "我想要什么" │               │ "怎么做"     │
  │ 描述最终状态  │               │ 列出操作步骤  │
  │ Terraform    │               │ Ansible      │
  │ CloudFormation│              │ Shell Script │
  │ Pulumi       │               │ Chef         │
  └─────────────┘               └─────────────┘
```

**声明式的优势：**
- 幂等性 — 多次执行结果一致
- 状态管理 — 自动感知漂移（drift）
- 代码即文档 — 配置文件就是架构图

### 3.2 Terraform 生命周期

```
init  →  fmt  →  validate  →  plan  →  apply  →  destroy
 │        │          │           │        │          │
 │        │          │           │        │          └─ 清理资源
 │        │          │           │        └──────────── 创建/更新资源
 │        │          │           └─────────────────── 预览变更计划
 │        │          └─────────────────────────────── 检查配置语法
 │        └────────────────────────────────────────── 格式化代码
 └───────────────────────────────────────────────── 初始化 provider
```

### 3.3 Terraform 核心文件结构

```
terraform/
├── main.tf          # 主配置文件（资源定义）
├── variables.tf     # 变量声明
├── outputs.tf       # 输出值
├── terraform.tfvars # 变量赋值（敏感信息）
└── provider.tf      # 云提供商配置
```

### 3.4 核心概念速记

| 概念 | 说明 |
|------|------|
| **Provider** | 云提供商插件（alicloud/aws/gcp） |
| **Resource** | 基础设施资源（ecs_instance, oss_bucket） |
| **Data Source** | 查询已有资源信息 |
| **State** | 当前基础设施状态映射文件（terraform.tfstate） |
| **Module** | 可复用的配置模板 |
| **Workspace** | 隔离不同环境（dev/staging/prod） |

> ⚠️ **重要教训**：state 文件包含敏感信息（密码、密钥），必须加密存储！远端存储用 OSS/S3 + DynamoDB 锁。

## 4. CI/CD 部署流水线

### 4.1 标准流水线架构

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│  代码提交  │ → │  单元测试  │ → │  构建    │ → │  集成测试  │ → │  部署    │
│  git push  │   │ pytest    │   │ build    │   │ staging  │   │ production│
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

### 4.2 部署策略对比

| 策略 | 描述 | 风险 | 适用场景 |
|------|------|------|----------|
| **蓝绿部署** | 两套完全相同的环境，切换流量 | 低 | 关键业务、数据库兼容 |
| **滚动更新** | 逐个替换实例 | 中 | 无状态服务、水平扩展 |
| **金丝雀发布** | 先升级小比例实例验证 | 低 | 新功能灰度验证 |
| **A/B 测试** | 不同版本同时运行，按比例分流 | 低 | 功能对比、数据验证 |

### 4.3 CI/CD 最佳实践清单

- [ ] **流水线即代码** — CI/CD 配置纳入版本控制
- [ ] **尽早失败** — 在编译/单元测试阶段就拦截错误
- [ ] **不可变部署** — 每次部署生成新镜像，不修改运行中环境
- [ ] **自动回滚** — 健康检查失败自动回退到上一个稳定版本
- [ ] **幂等部署脚本** — 重复执行不产生副作用
- [ ] **环境一致性** — dev/staging/prod 配置参数分离，基础设施一致
- [ ] **状态管理** — 数据库变更与代码变更分开管理

## 5. 跨云部署注意事项

### 5.1 接口一致性与抽象层

```
应用层
  │
  ├── 直接服务商 API（高性能，但锁定）
  │     └── 阿里云 SDK / AWS SDK
  │
  ├── 多云框架（统一抽象，有抽象损失）
  │     └── Terraform / Pulumi / Crossplane
  │
  └── 云原生标准（最高可移植性）
        └── Kubernetes / OpenStack / Serverless Framework
```

### 5.2 成本差异要点

| 服务 | 阿里云 | AWS | 提示 |
|------|--------|-----|------|
| 出站流量 | 较便宜(0.8元/GB) | 较贵($0.09/GB) | AWS 流量是成本大头 |
| 对象存储 GET 请求 | 约 0.01元/万次 | $0.0004/万次 | AWS 请求费低但存储费高 |
| 负载均衡 | 按实例+带宽计费 | 按 LCU 用量计费 | 低流量时 AWS 更便宜 |
| NAT 网关 | 按规格包月 | 按处理数据量 | 小流量用阿里云更便宜 |

### 5.3 跨云架构模式

**Active-Active (双活)：**
- 两个云同时服务，DNS 做地理调度
- 复杂度高，需解决数据同步和一致性问题

**Active-Passive (主备)：**
- 主云承载流量，备云冷备或只读
- 故障时 DNS 切换 + 数据恢复

**按服务拆分：**
- 计算在 A 云，存储/数据库在 B 云
- 延迟和成本需要权衡

### 5.4 跨云迁移 checklist

1. 评估依赖关系（DNS、证书、第三方 API）
2. 数据迁移方案（全量 + 增量同步）
3. 割接窗口和时间预算
4. 回滚计划（确认旧环境可快速恢复）
5. 监控和告警迁移
6. DNS 切换（TTL 提前降低）

## 6. 安全最佳实践

### 6.1 最小权限原则 (Principle of Least Privilege)

```
      需要权限
   ┌─────┴─────┐
   │            │
允许           拒绝
(白名单)      (默认策略)
```

**实践方法：**
- IAM/RAM 策略：只给角色分配完成任务所需的最小权限
- 临时凭证：使用 STS 短期凭证，避免长期 AccessKey
- 资源级权限：限制用户只能操作特定资源（如特定 Bucket）
- 职责分离：开发、测试、运维使用不同角色

### 6.2 密钥管理

| 密钥类型 | 存储方式 | 风险 |
|----------|----------|------|
| AccessKey/SecretKey | 环境变量 / KMS / 密钥管理服务 | ⚠️ 不在代码中硬编码 |
| SSH 密钥对 | 私钥本地加密存储 + 密码保护 | ⚠️ 不传输明文 |
| 数据库密码 | KMS / Secrets Manager | ⚠️ 定期轮换 |
| TLS/SSL 证书 | 证书管理服务 (Cert Manager) | ⚠️ 监控过期时间 |

**黄金法则：**
> **密钥永远不提交到代码仓库** — 即使用于测试也不行。

### 6.3 安全组规则最佳实践

```
🚫 错误做法：
  入方向 0.0.0.0/0 :22 (SSH 全网开放)
  入方向 0.0.0.0/0 :3306 (MySQL 全网开放)

✅ 正确做法：
  入方向 <办公IP>/32 :22      (仅允许公司 IP SSH)
  入方向 <应用SG> :3306       (仅允许同安全组数据库连接)
  入方向 0.0.0.0/0 :80        (HTTP 全网 — 必要)
  入方向 0.0.0.0/0 :443       (HTTPS 全网 — 必要)
```

**安全组设计原则：**
1. 一个安全组只做一件事（WebSG、DBSG、AppSG）
2. 使用安全组引用而不是 CIDR 来连接内部服务
3. 定期审计安全组规则（检查未使用的开放端口）
4. 删除默认放行的出方向规则（出方向也要最小权限）

### 6.4 其他安全要点

- **网络隔离**：公网服务放 DMZ 区，数据库和内务服务放私网
- **日志和审计**：开启操作审计 (ActionTrail / CloudTrail)
- **WAF**：Web 应用防火墙防御 SQL 注入、XSS、CC 攻击
- **DDoS 防护**：启用云防护基础版 + 高防 IP（如果必要）
- **定期渗透测试**：发现配置漏洞和逻辑缺陷

## 7. 实战Demo 架构说明

见 `projects/cloud_deploy/demo/` 目录下的完整实战演示。

### 文件结构

```
projects/cloud_deploy/demo/
├── deploy.py        # 部署入口脚本
├── deploy_base.py   # 云部署模拟引擎（模拟 ECS/安全组/SLB 等）
├── web_app.py       # 纯 Python socket 实现的 HTTP 服务器
└── test_demo.py     # 19 个测试用例
```

### 部署流程 (对应真实云部署)

| 步骤 | 函数 | 说明 | 对应云服务 |
|------|------|------|-----------|
| 1 | `step_init_server()` | 初始化服务器配置 | 选择 VPC/Region |
| 2 | `step_create_security_group()` | 创建安全组+入站规则 | 阿里云安全组 / AWS Security Group |
| 3 | `step_create_ecs()` | 创建 ECS 实例 | 阿里云 ECS / AWS EC2 |
| 4 | `step_upload_code()` | 上传应用代码 | SCP/FTP/CI 工具 |
| 5 | `step_start_service()` | 启动 Web 服务 | systemd / supervisor |
| 6 | `step_health_check_http()` | 健康检查 | SLB/ALB 健康检查 |
| 7 | `step_configure_slb()` | 配置负载均衡 | 阿里云 SLB / AWS ALB |

### 关键技术点

- **零外部依赖** — 用 Python `socket` 原生实现 HTTP 服务器
- **健康检查** — 先 TCP 端口检测，再 HTTP `/health` 接口检测
- **并发测试** — 验证多线程请求处理能力
- **19 个测试全覆盖** — 引擎步骤、服务器端点、集成测试
