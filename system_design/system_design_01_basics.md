## 1. 事务与一致性模型

### ACID（关系型数据库）
- **Atomicity（原子性）**：事务要么全做，要么全不做。通过 undo log 实现回滚。
- **Consistency（一致性）**：事务前后数据满足所有约束。应用层+数据库层共同保证。
- **Isolation（隔离性）**：并发事务互不干扰。通过锁/MVCC 实现。
- **Durability（持久性）**：提交后数据永久保存。通过 redo log 实现。

### CAP 定理
分布式系统最多同时满足两项：
- **Consistency（一致性）**：所有节点同一时刻看到相同数据
- **Availability（可用性）**：每个请求都能获得（非错误）响应
- **Partition Tolerance（分区容忍性）**：网络分区时系统仍能工作

**P 是必选项**（分布式网络总有分区可能）：
- **CP 系统**：分区时牺牲可用性，等待数据一致（ZooKeeper、etcd）
- **AP 系统**：分区时牺牲一致性，返回旧数据（Cassandra、DNS）

### BASE（NoSQL/分布式系统）
- **Basically Available（基本可用）**：允许部分故障，核心功能可用
- **Soft State（软状态）**：状态可以随时间变化（不要求实时一致）
- **Eventually Consistent（最终一致）**：一段时间后，所有副本最终一致

对比：
| 属性 | ACID | BASE |
|------|------|------|
| 哲学 | 悲观（预防问题） | 乐观（容忍问题） |
| 一致性 | 强一致 | 最终一致 |
| 适用 | 金融、订单 | 社交、缓存、日志 |

## 2. 架构模式

### 单体架构（Monolithic）
所有功能在单个进程中，共享数据库。

**优点**：
- 开发简单，调试容易
- 事务一致性好
- 部署简单

**缺点**：
- 代码耦合，难以扩展
- 改一行影响整个系统
- 技术栈锁定

### 微服务架构（Microservices）
每个业务模块独立进程，通过 API 通信。

**优点**：
- 独立部署、独立扩展
- 技术栈灵活
- 故障隔离

**缺点**：
- 分布式复杂性（网络延迟、数据一致性）
- 运维成本高（监控、日志聚合、服务发现）
- 调试困难

**适用场景判断**：
```
团队 < 10人 → 单体起步，按模块分包
团队 > 10人 → 考虑微服务
流量峰值比 > 10x → 需独立扩缩容
```

### SOA vs 微服务
- **SOA**：企业级服务总线(ESB)，服务间通过消息中间件通信
- **微服务**：去中心化，直接 HTTP/gRPC 通信，轻量级

## 3. CQRS（命令查询职责分离）

核心思想：**读操作和写操作使用不同的模型**。

```
Command（写） → Command Handler → Write DB
Query（读）   → Query Handler   → Read DB（可能是缓存/物化视图）
```

**为什么分离**：
- 读写负载不对称（90%读10%写）
- 读模型可以针对查询优化（反范式、缓存）
- 写模型保持业务逻辑完整

**结合事件溯源（Event Sourcing）**：
- 不存当前状态，存事件流
- 当前状态 = 事件流回放结果
- Read DB = 事件流的物化视图
- 天然审计日志、时间旅行、CQRS 自动同步

```python
# 写模型：事件
Event Store:
  [UserCreated, EmailChanged, PasswordReset, ...]

# 读模型：物化视图
Read Model:
  { userId: "...", email: "...", name: "..." }
```

## 4. 事件溯源（Event Sourcing）

不存储实体当前状态，存储导致状态变更的事件序列。

**优点**：
- 完整审计追踪
- 可回溯到任意时间点
- 天然支持 CQRS
- 松耦合（事件生产者和消费者独立）

**缺点**：
- 查询复杂（需回放事件）
- 存储量大
- 事件模式演进困难（需版本兼容）

## 5. 架构对比一览

| 模式 | 一致性 | 伸缩性 | 复杂度 | 适用场景 |
|------|--------|--------|--------|---------|
| 单体+ACID | 强 | 差 | 低 | 小团队、内部系统 |
| 微服务+AP | 最终 | 好 | 高 | 大流量、快速迭代 |
| CQRS+EventSourcing | 最终 | 好 | 中高 | 审计、协作、报表 |
| 读写分离 | 弱一致 | 中 | 中 | 博客、内容站 |

## 核心原则
1. **CAP 中 P 是必选** — 分区一定会发生，选择 CP 还是 AP 是 trade-off
2. **拒绝过早微服务** — 单体并不羞耻，微服务不解决所有问题
3. **查询和命令天然不同** — CQRS 不是过度设计，是承认读写不平等
4. **事件溯源是 CQRS 的最佳伙伴** — 但不是银弹
