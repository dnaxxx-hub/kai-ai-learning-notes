# 故障响应 — Severity 分级 / On-call / Incident 流程 / 复盘 / 工具

## 一、Severity 分级与 SLA

### P0-P3 标准定义

| 级别 | 定义 | 响应时间 | 恢复时间(SLA) | 示例 |
|------|------|----------|---------------|------|
| **P0** | 核心服务完全不可用，影响全部用户 | ≤ 5min | ≤ 1h | 登录/支付全线挂 |
| **P1** | 核心服务严重受损，影响大量用户 | ≤ 15min | ≤ 4h | 核心 API 错误率 > 20% |
| **P2** | 非核心服务受损或部分用户受影响 | ≤ 1h | ≤ 24h | 某地区访问慢、非核心功能异常 |
| **P3** | 不影响功能的低优先级问题 | ≤ 1d | ≤ 7d | UI 样式错乱、日志不完整 |

### 关键要点
- **P0/P1 需要即时通知**：电话/PagerDuty，24h 响应
- **P2 工作时间内响应**：工单系统，Slack 通知
- **P3 排期修复**：Backlog 管理，定期评审
- **升级（Escalation）**：P0 在 15min 无人认领 → 自动升级到 Tech Lead → 30min → 经理

## 二、On-call 轮值

### 轮值制度
- **轮班制**：一周轮换（Mon-Sun），支持 Second Level（后备）
- **Follow-the-Sun**：跨国团队接力（白天接力，避免夜间 On-call）
- **Time-to-ack**：P0 5min 内 acknowledged，超时自动升级

### 告警升级路径（Escalation）
```
Primary On-call (5min)
  ↓ No Ack
Secondary / Backup On-call (10min)
  ↓ No Ack  
Tech Lead (15min)
  ↓ No Ack
Engineering Manager (20min)
  ↓ No Ack
VP / Director (30min)
```

### On-call 最佳实践
- **Handover 文档**：交接班时同步当前 Incident 状态
- **Pre-alert Check**：重大变更前（发布到生产环境）提前知会 On-call
- **合理负担**：On-call 后 24h 不参与重大变更
- **补偿机制**：On-call 轮值人员有调休或额外补贴

## 三、Incident 流程

### 五阶段标准流程

```
发现 → 诊断 → 缓解 → 解决 → 复盘
```

#### 1. 发现（Detection）
- 自动化告警（Prometheus/Alertmanager）
- 用户投诉 → Support 确认 → 转 Incident
- 合成监控（Synthetic Monitoring）发现

#### 2. 诊断（Diagnosis）
```
1. 看 Metrics Dashboard → 确认异常范围
2. 检查 Change Log → 最近一次变更是什么
3. 关联 Tracing → 找到慢的 Trace
4. 搜索 Logs → 获取具体错误堆栈
```
- **经验性诊断**：根据历史故障模式快速判断（如 MySQL 慢查询 → 先看慢查询日志）

#### 3. 缓解（Mitigation）
- **目标是恢复服务，不是找根因**
- 常见手段：回滚部署、重启服务、切流量、扩容、限流降级
- **SEV fixed** 后继续保留在会议中，直到确认恢复稳定

#### 4. 解决（Resolution）
- 确认根因修复
- 监控指标恢复至基线
- 确认无残留影响

#### 5. 复盘（Postmortem / Retrospective）
- **Blame-free** 文化：不追责个人，查找系统缺陷
- **行动项**：具体、可量化、有负责人和截止日期

## 四、事后复盘（Postmortem）

### 5 Whys 分析法
```
问题：支付服务宕机 30min

Why 1: 数据库连接池耗尽
Why 2: 促销活动流量比预期高 5 倍
Why 3: 促销活动未做压测
Why 4: 发布流程中缺少压测环节
Why 5: 基础设施团队未与业务团队对齐发布标准
           ↓
根因：发布流程缺少压测检查 → 行动项：发布前必须通过压测 Gate
```

### 复盘模板
```markdown
# 故障复盘报告

## 基本信息
- 时间：2025-01-15 14:30 - 15:00 UTC
- 级别：P0
- 影响：全部用户无法支付（约 5 万用户受影响）
- MTTR：30min

## 时间线
| 时间 | 事件 |
|------|------|
| 14:30 | 告警触发，错误率飙升 |
| 14:32 | On-call 确认 |
| 14:35 | 诊断：数据库连接池打满 |
| 14:40 | 缓解：重启数据库连接池（临时恢复） |
| 14:45 | 确认服务恢复 |
| 14:50 | 根因定位：慢查询导致连接不释放 |
| 15:00 | 创建慢查询索引，正式修复 |

## 根因分析（5 Whys）
- 促销活动流量涌入 → 慢查询（缺少索引）→ 连接池耗尽

## 行动项
| 行动项 | 负责人 | 截止日期 | 状态 |
|--------|--------|----------|------|
| 添加慢查询索引 | 张三 | 1/16 | ✅ |
| 压测 Gate 加入 CI | 李四 | 1/30 | 🏗️ |
| 连接池监控告警 | 王五 | 1/20 | 🔲 |
```

### 知识沉淀
- 复盘报告存档（Confluence / Git 仓库）
- Runbook 更新（下一次遇到同类问题可直接参考）
- 告警规则优化（补充缺失的告警、去除噪音告警）

### 选择建议
- **PagerDuty**：国际团队、多通知渠道、完善的 Incident 管理
- **OpsGenie**：性价比优于 PagerDuty，功能接近
- **PrometheusAlert**：国内团队、开源、深度集成飞书/钉钉/微信
- **平台原生**：小型团队可直接用飞书/Slack 的 webhook + 轮值日历
