## 1. AI Infra 是什么

### 定义

AI Infra = 支撑AI系统从训练到推理的全部基础设施。

```
AI Infra 分层：
┌──────────────────────────────────────┐
│  应用层                              │
│  ChatGPT / Claude / 量化交易         │
├──────────────────────────────────────┤
│  AI系统层                            │
│  Training / Fine-tuning / Inference  │
├──────────────────────────────────────┤
│  框架层                              │
│  PyTorch / TensorFlow / MLX / CUDA   │
├──────────────────────────────────────┤
│  调度层                              │
│  Kubernetes / Slurm / Ray            │
├──────────────────────────────────────┤
│  硬件层                              │
│  GPU / NPU / TPU / RDMA / NVLink     │
└──────────────────────────────────────┘
```

### 核心挑战

```
1. 算力利用率 —— 如何让GPU不闲着
   → 数据中心GPU平均利用率 30-50%
   → 优化目标: 70%+

2. 内存墙 —— GPU显存有限
   → H100: 80GB HBM3
   → 70B模型FP16需要140GB → 张量并行横跨2卡

3. 通信墙 —— 跨卡通信开销
   → NVLink: 900GB/s (8卡)
   → RDMA: 200GB/s (跨节点)
   → 网络延迟: 1-10μs

4. 可靠性 —— 训练跑几天/几周不出错
   → 每1000 GPU-hours约1次故障
   → 需要checkpoint + 自动恢复
```

## 2. 训练基础设施

### 2.1 并行策略选择

```
┌──────────────┬────────────────┬──────────────────┬─────────────────────────┐

├──────────────┼────────────────┼──────────────────┼─────────────────────────┤

├──────────────┼────────────────┼──────────────────┼─────────────────────────┤

│              │                 │  ~hidden×seq     │ 8卡做TP最佳               │
├──────────────┼────────────────┼──────────────────┼─────────────────────────┤
│  Pipeline并行  │ 1x (N卡流水线)  │ Pipe边界低频通信   │ 显存有限/跨节点            │
│              │                 │  ~layer×hidden    │ 可配Gpipe/1F1B           │
├──────────────┼────────────────┼──────────────────┼─────────────────────────┤
│  序列并行      │ 1x             │ 跨卡seq chunk     │ 长上下文(>32K)            │
│              │                 │  flash attention  │                          │
└──────────────┴────────────────┴──────────────────┴─────────────────────────┘
```

### 2.2 典型部署方案

**方案1：单机8卡（H100 × 8 = 640GB HBM3）**

```
7B模型 (14GB FP16):
  数据并行    → 每个GPU一份模型，各跑不同batch
  性价比最高，显存完全够用

70B模型 (140GB FP16):
  张量并行(TP=8) → 横跨8卡，每个GPU存储1/8权重
  通信瓶颈在卡间NVLink (900GB/s) → 够快
  → 单机8卡最佳方案

180B模型 (360GB FP16):
  TP=8 + PP=3(pipe) → 需要3节点24卡
  TP在节点内 (NVLink)
  PP跨节点 (RDMA)
```

## 3. 推理基础设施

### 3.1 推理集群架构

```
                   ┌──────────────┐
                   │   Load       │
                   │   Balancer   │
                   └──────┬───────┘
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
         ┌────────┐ ┌────────┐ ┌────────┐
         │ Router │ │ Router │ │ Router │
         │ Node   │ │ Node   │ │ Node   │
         └───┬────┘ └───┬────┘ └───┬────┘
              │           │           │
    ┌─────────┼─────────┐│┌─────────┼─────────┐
    ▼         ▼         ▼▼▼         ▼         ▼
 ┌────┐   ┌────┐   ┌────┐   ┌────┐   ┌────┐   ┌────┐
 │GPU │   │GPU │   │GPU │   │GPU │   │GPU │   │GPU │
 │N1  │   │N2  │   │N3  │   │N4  │   │N5  │   │N6  │
 └────┘   └────┘   └────┘   └────┘   └────┘   └────┘

Router Node 职责:
  1. 请求验证 + Tokenize
  2. 路由到最空闲的GPU节点（根据当前负载和KV利用率）
  3. 流式响应聚合
  4. 错误处理（降级/重试）
```

### 3.2 KV Cache 的分布式管理

单机80GB HBM3：
```
70B模型 INT4 → ~42GB权重占用
剩余 → ~38GB 可用KV Cache

每token KV Cache ≈ 8KB (FP8)
→ 38GB / 8KB ≈ 4.8M tokens
→ batch=32, avg_seq=2K → 32×2K=64K
→ 4.8M / 64K = 75 batch之间可用
→ 约75个并发请求同时推理
```

### 3.3 弹性扩展

```yaml
# 推理集群自动扩缩容配置
auto_scaling:
  metric: gpu_kv_cache_utilization
  scale_up_threshold: 85%   # KV利用率>85%触发扩容
  scale_down_threshold: 30% # KV利用率<30%触发缩容
  min_instances: 4
  max_instances: 32
  cooldown: 300s           # 5分钟不重复触发
```

### 5.2 故障恢复

```python
class FaultHandler:
    def handle_gpu_failure(gpu_id):
        # 1. 标记节点不可用
        mark_node_unavailable(gpu_id)
        
        # 2. 迁移训练任务
        if is_training(gpu_id):
            latest_checkpoint = find_latest_checkpoint()
            resume_training(
                checkpoint=latest_checkpoint,
                exclude_gpus=[gpu_id]
            )
        
        # 3. 迁移推理任务
        if is_inference(gpu_id):
            for req in active_requests[gpu_id]:
                # 推理不需要恢复，直接重试
                re_route_to_spare_gpu(req)
        
        # 4. 通知SRE
        send_alert(f"GPU {gpu_id} failed, traing resumed from step {step}")
```

## 6. 成本分析（以H100集群为例）

```
┌──────────────┬──────────┬───────────┬──────────┐
│  项目         │  训练cluster  │  推理cluster  │  备注     │
├──────────────┼──────────┼───────────┼──────────┤
│  单卡H100     │ $3/h     │ $3/h      │ 按需价格    │
│  集群规模      │ 1024卡    │ 512卡      │           │
│  月硬件成本    │ $2.2M    │ $1.1M     │           │
│  网络+存储     │ $300K    │ $150K     │ RDMA+NAS │
│  电力+冷却     │ $200K    │ $100K     │ ~15-20%  │
│  运维人力      │ $500K    │ $300K     │ SRE/MLOps│

│  总月成本      │ ~$3.2M    │ ~$1.65M    │           │
└──────────────┴──────────┴───────────┴──────────┘

成本优化策略:
  1. 用Spot实例做训练（训练可中断恢复）→ 省60%
  2. 推理用按需（不能中断服务）
  3. 量化+蒸馏减少GPU需求 → 推理集群缩小50%
  4. 在低谷时段（凌晨）做训练checkpoint恢复
```
