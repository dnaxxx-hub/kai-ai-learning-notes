# 第3课：QUIC加密与安全

> 参考 RFC 9001（Using TLS to Secure QUIC）

---

## 3.1 TLS 1.3集成（不是TLS over TCP）

### 核心设计理念

QUIC 没有像传统做法那样在 TCP 上跑 TLS（即 TLS Record 协议），而是**将 TLS 1.3 握手直接集成到 QUIC 传输层中**。

```
传统 TLS over TCP:              QUIC 的 TLS 集成:
┌────────────────────┐          ┌────────────────────┐
│   应用数据          │          │   应用数据          │
├────────────────────┤          ├────────────────────┤
│   TLS Record       │          │   QUIC Frame       │
│   (加密/解密)      │          │   (加密/解密)      │
├────────────────────┤          ├────────────────────┤
│   TCP 传输         │          │   QUIC 传输        │
├────────────────────┤          ├────────────────────┤
│   IP 网络          │          │   UDP + IP         │
└────────────────────┘          └────────────────────┘
```

### TLS 1.3 在 QUIC 中的角色

1. **身份认证**：服务器证书验证（可选客户端证书）
2. **密钥导出**：握手过程产生 5 组密钥：
   - Initial 密钥（静态派生，非完美前向安全）
   - Handshake 密钥（完美前向安全）
   - 1-RTT 发送密钥 + 接收密钥（应用数据）
2. **传输参数协商**：TLS 扩展 `quic_transport_parameters` 携带 QUIC 特有的参数（如初始流控窗口、最大流数量等）

### 与 TLS over TCP 的关键差异

| 特性 | TLS over TCP | QUIC TLS 集成 |
|------|-------------|---------------|
| 记录层 | TLS Record (ContentType + 长度) | QUIC Stream + CRYPTO 帧 |
| 握手传输 | TCP 字节流 | CRYPTO 帧（在流 0 上传输，但独立于流层） |
| 密钥更新 | 通过 TLS KeyUpdate 消息 | QUIC 的 KEY_PHASE 位 + 派生密钥 |
| 0-RTT | TLS 1.3 0-RTT（通过 early_data 扩展） | CRYPTO 帧独立 + QUIC 0-RTT 包加密 |
| 握手保护 | TLS 1.3 自带 | 无额外保护（重用 TLS 握手） |

## 3.2 握手过程：Initial → Handshake → 1-RTT

### 完整的 QUIC 1-RTT 握手

```
阶段 1/3: Initial (加密: 初始密钥)
┌───────────────────────────────────────────┐
│ 客户端 (Initial Key)                      │
│  ┌─ Initial 包 ────────────────────────┐  │
│  │ CRYPTO Frame: ClientHello          │  │
│  │   - TLS 版本: 1.3                  │  │
│  │   - 密码套件: TLS_AES_128_GCM_SHA256│  │
│  │   - Key Share: X25519              │  │
│  │   - QUIC传输参数:                   │  │
│  │     initial_max_data              │  │
│  │     initial_max_streams_uni       │  │
│  │     initial_max_stream_data_bidi  │  │
│  │     ...                           │  │
│  │ PADDING (满足 1200 字节 MTU)      │  │
│  └───────────────────────────────────┘  │
│  ┌─ 可以带 ACK 帧 ─────────────────────┐ │
│  └──────────────────────────────────────┘│
└───────────────────────────────────────────┘
           │
           ▼
┌───────────────────────────────────────────┐
│ 服务器 (Initial Key 解密 ClientHello)     │
│  ┌─ Initial 包 ────────────────────────┐  │
│  │ ACK Frame                           │  │
│  │ CRYPTO Frame: ServerHello          │  │
│  │   - 选择密码套件                    │  │
│  │   - 服务器 Key Share               │  │
│  │   - QUIC传输参数                    │  │
│  └─────────────────────────────────────┘  │
│  ┌─ Handshake 包 ──────────────────────┐  │
│  │ CRYPTO Frame: EncryptedExtensions  │  │
│  │ CRYPTO Frame: Certificate          │  │
│  │ CRYPTO Frame: CertificateVerify    │  │
│  │ CRYPTO Frame: Finished             │  │
│  └─────────────────────────────────────┘  │
│  ┌─ 1-RTT 包 ──────────────────────────┐  │
│  │ HANDSHAKE_DONE 帧                   │  │
│  └─────────────────────────────────────┘  │
└───────────────────────────────────────────┘
           │
           ▼
阶段 3/3: 客户端完成握手
┌───────────────────────────────────────────┐
│ 客户端                                     │
│  ┌─ Handshake 包 ───────────────────────┐  │
│  │ CRYPTO Frame: Finished              │  │
│  └─────────────────────────────────────┘  │
│  ┌─ 1-RTT 包 ──────────────────────────┐  │
│  │ STREAM Frame: HTTP GET /           │  │  ← 真正的应用数据！
│  └─────────────────────────────────────┘  │
└───────────────────────────────────────────┘
```

### 密钥推导层级

```
初始密钥 (Initial Secrets)
  ├── 客户端初始密钥 (client_initial_secret)
  │     └── 由 DCID 和静态 salt 派生
  │     ├── 客户端写密钥 (用于加密 Initial 包)
  │     └── 服务器读密钥 (用于解密 Initial 包)
  │
  ├── 服务器初始密钥 (server_initial_secret)
  │     └── 由 DCID 和静态 salt 派生
  │
  ├── 握手密钥 (Handshake Secrets)
  │     └── 由 (EC)DHE 交换派生 → 完美前向安全
  │
  ├── 1-RTT 流量密钥 (Traffic Secrets)
  │     └── 由握手密钥 + Finished 消息派生
  │
  └── 0-RTT 密钥 (0-RTT Secrets)
        └── 由之前会话的 PSK 派生
```

**Initial 密钥的特殊性**：
- 使用固定的 salt `0x38762cf7f55934b34d179ae6a4c80cadccbb7f0a`
- 因此 Initial 包内容可以被任何知道 DCID 的人解密（不提供完美前向安全）
- 设计目的：防止中间盒篡改，而不是提供机密性

## 3.3 0-RTT数据的安全属性

### 0-RTT 的工作原理

```
首次连接 (完整 1-RTT):
客户端                        服务器
  │ 握手完成                    │
  │                            │
  │←──── NEW_TOKEN ───────────│  ← 服务器发放地址 Token
  │←──── 会话票据 (Session Ticket) │  ← 包含 PSK
  │                            │

后续连接 (0-RTT):
客户端                        服务器
  │                            │
  │──Initial + 0-RTT Data────→│  ← 立即发数据！
  │   (使用缓存的 PSK 加密)     │
  │                            │
  │←──1-RTT Response─────────│
```

### 0-RTT 的安全风险

#### 1. 重放攻击（Replay Attack）

攻击者截获 0-RTT 请求后，可以重复发送给服务器：

```
攻击者: ──0-RTT "转账1000元"──→ 服务器
攻击者: ──0-RTT "转账1000元"──→ 服务器 (第二次)
攻击者: ──0-RTT "转账1000元"──→ 服务器 (第三次)
```

**防御措施**：
- 服务器实现重放检测（如使用 Replay Cache）
- 幂等操作才适合 0-RTT
- QUIC 要求服务器限制 0-RTT 数据量

#### 2. 前向安全问题

如果长期密钥泄露，攻击者可以解密之前记录的 0-RTT 数据。这是因为 0-RTT 密钥基于 PSK（长期密钥），而非临时 (EC)DHE 密钥。

```
PSK 泄露 → 所有 0-RTT 会话都被解密
而 1-RTT 数据有 (EC)DHE → 即使 PSK 泄露也无影响
```

#### 3. 降级攻击

攻击者可以阻止客户端收到服务器的 NEW_TOKEN 和会话票据，从而阻止 0-RTT。这不是严重的安全问题，但会降级性能。

### QUIC 的安全协议栈总结

```
机密性保障：
┌──────────────────────────────────────┐
│ Initial 包: 低级 (静态密钥)          │ ← 防篡改，不保密
│ Handshake 包: 强 (EC)DHE             │ ← 完美前向安全
│ 1-RTT 包: 强 (EC)DHE                 │ ← 完美前向安全
│ 0-RTT 包: 中 (PSK)                   │ ← 无完美前向安全
└──────────────────────────────────────┘
```

## 3.4 密钥更新

QUIC 支持在连接生命周期内多次更新 1-RTT 密钥：

### Key Phase 机制

QUIC Short Header 包含 1 位 `Key Phase` 标志：

```
Key Phase = 0: 使用当前阶段密钥
Key Phase = 1: 使用新阶段密钥（更新后）

更新流程：
1. 发送方切换 Key Phase (0→1 或 1→0)
2. 使用新密钥加密数据包
3. 接收方收到 Key Phase 变换的数据包后：
   a. 尝试用新密钥解密
   b. 成功 → 更新本地方密钥
   c. 失败 → 发送 KEY_UPDATE 帧触发更新
```

### 密钥更新过程

```
发送方                             接收方
  │   (当前 Phase=0)                │
  │                                 │
  │──Phase=1 数据包───────────────→│  ← 接收方检测到 Phase 变化
  │                                 │  ← 尝试用新阶段密钥解密
  │                                 │  ← 成功，更新密钥
  │←──Phase=1 ACK─────────────────│  ← 确认收到新 Phase
  │                                 │
  │   (双方都在 Phase=1)            │
```

### 密钥更新的优势

1. **限制密钥泄露影响** — 即使当前密钥泄露，之前的通信仍然是安全的（向前安全）
2. **符合密码学最佳实践** — 同一密钥加密的数据量有上限
3. **主动防御** — 如果怀疑密钥泄露，可以立即更新

### 更新限制

- 每次更新后，旧阶段的密钥被丢弃（不能回退）
- 一个连接最多 2^63 次密钥更新（实际远小于此）

## 附加安全机制

### 地址验证（Address Validation）

- **Retry 包**：服务器发 Challenge Token，客户端需在 Initial 包中返回
- **NEW_TOKEN**：连接建立后服务器发放，下次 0-RTT 可用
- **PATH_CHALLENGE/PATH_RESPONSE**：连接迁移时验证新路径

### 防放大攻击（Amplification Attack Limitation）

- 服务器在验证客户端地址前，发送数据总量不超过接收数据量的 **3 倍**
- 如果客户端发送 1200 字节 Initial，服务器最多回复 3600 字节
- 直到收到 Handshake 完成验证，限制解除

### 连接关闭的优雅性

- CLOSE_CONNECTION 帧携带错误码和人类可读原因
- 收到 CLOSE_CONNECTION 后，对端应回复 CLOSE_CONNECTION 或静默关闭
- 超时关闭（Idle Timeout）— 默认 30 秒无数据则关闭

---

## 一句话总结

QUIC 将 TLS 1.3 握手嵌入传输层，通过 Initial→Handshake→1-RTT 三阶段加密实现了 1-RTT 安全建连，0-RTT 提供了性能优化但牺牲了前向安全性和重放保护。
