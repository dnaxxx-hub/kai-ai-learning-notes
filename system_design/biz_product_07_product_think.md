# 课时7：产品思维——从 JTBD 到决策框架

> 面向对象：AI/技术从业者
> 核心命题：如何像顶级 PM 一样思考，做出更好的产品决策

## 一、为什么技术人需要产品思维？

最优秀的技术人，不是编码最快的，而是**能用系统思维做产品决策**的。

**两类技术人的对比**：

| 维度 | 纯技术思维 | 产品思维 |
|------|-----------|---------|
| 接到需求 | "这需求怎么实现？" | "用户为什么要这个？这真的是最好的解法吗？" |
| 面对争议 | "我的方案技术最优" | "方案 A 的用户价值 vs 方案 B 的开发成本，哪个更划算？" |
| 优先级判断 | "技术复杂度高的排前面" | "用户影响最大的排前面" |
| 价值衡量 | "多好用啊" | "用户愿意为此付费/花时间吗？" |

**产品思维不是取代技术判断**，而是在技术判断之外增加一层**用户价值和商业价值的判断维度**。

## 二、JTBD（Jobs To Be Done）——用户不是想要钻头，而是想要一个洞

### 2.1 JTBD 核心思想

**Jobs To Be Done（需要完成的任务）** 是 Clayton Christensen 教授提出的理论框架。

核心观点：**用户购买的不是产品，而是通过产品完成某个"任务"**。

```
用户买电钻 → 不是想要电钻，而是想要墙上的洞
用户订外卖 → 不是想要外卖，而是想要"不用做饭"
用户用 ChatGPT → 不是想要 LLM，而是想要"不用自己写"
```

### 2.2 JTBD 的三种类型

| 类型 | 定义 | 例子 |
|------|------|------|
| 功能型任务（Functional Job） | 用户想完成的具体事情 | "我要从 A 到 B" |
| 情感型任务（Emotional Job） | 用户想感受到什么 | "我想显得很专业" |
| 社交型任务（Social Job） | 用户想在他人面前是什么形象 | "我想让同事觉得我很酷" |

**一个外卖 App 的三种 JTBD**：

| 场景 | 功能型任务 | 情感型任务 | 社交型任务 |
|------|-----------|-----------|-----------|
| 午餐 | 填饱肚子 | 不用出公司 | 和同事一起点显得合群 |
| 周末晚餐 | 和伴侣吃好点 | 享受不洗碗的放松 | 发 "今天做了顿好的" 到朋友圈 |
| 加班夜宵 | 补充能量继续工作 | 感到被犒劳 | — |

**关键 insight**：一个产品如果只满足功能型任务，很容易被替代。满足情感型和社交型任务才能形成壁垒。

### 2.3 JTBD 实战方法

**用户访谈的"5个为什么"**：
```
用户："我需要一个待办清单 App"
为什么？→ "因为我记不住要做的事"
为什么记不住？→ "因为事情太多，分散在不同的平台"
为什么事情多会导致记不住？→ "因为我需要切换不同工具看"
为什么切换工具是问题？→ "因为切换时我会忘记刚才想做什么"
→ 真正的 Job：需要"不丢失想法"的能力
→ 解法可能不是更好的待办清单，而是系统级的任务聚合
```

**JTBD 的竞争矩阵**：

| 任务 | 当前解决方案 | 痛点 | 机会 |
|------|------------|------|------|
| "快速写出专业邮件" | 手动写（15min/封） | 耗时、语法检查 | AI 辅助写作 |
| "管理项目进度" | Jira | 太重了、配置复杂 | Notion、Linear |
| "找好吃的" | 大众点评 | 刷评严重、信息过载 | 熟人推荐、小红书 |

### 2.4 案例：Superhuman 的 JTBD

**Superhuman**（¥210/月的邮件客户端）极度极致地体现 JTBD 思维。

**JTBD 定义**：
> "更快地处理完邮件，获得掌控感"

**功能映射**：
| 用户痛点 | JTBD | Superhuman 解法 |
|---------|------|----------------|
| 收件箱无穷无尽 | "尽快处理完邮件" | 一键归档、快捷键操作 |
| 打开邮件慢 | "不要浪费等待时间" | 预加载所有内容 |
| 不知道哪些邮件重要 | "先处理重要邮件" | AI 自动排序、高亮 |
| 邮件太多分心 | "不被邮件打扰" | 专注模式、批量处理 |

**结果**：用户平均处理速度比常规客户端快 3-5 倍，付费用户留存率 > 90%。

**给技术人的启示**：如果你在做一个 "更好的 XX"，先问自己三个 JTBD 问题：
1. 用户当前是怎么完成这个任务的？（现有方案）
2. 用户在这个任务中最大的痛点是什么？
3. 你的解决方案让完成这个任务快/好/省了多少？

## 三、PMF（Product-Market Fit）——如何验证产品做对了

### 3.1 什么是 PMF？

**PMF（Product-Market Fit，产品市场匹配）**：你的产品正好解决了某个市场迫切的需求。

**Marc Andreessen 的定义**：
> "PMF 就是你产品的价值（Value）清晰地超过了用户获得它的成本（包括价格、学习成本、迁移成本）。"

### 3.2 PMF 的度量

**Sean Ellis 测试（最常用）**：

> 问用户："如果这个产品明天消失了，你会有多失望？"
> - 非常失望 → PMF（40%+ 的用户选此项）
> - 有点失望 → 还行
> - 不失望 → 没找到 PMF

**Benchmark 标准**：
- 40%+ "非常失望"：找到 PMF，可以全力增长
- 25-40%：有关注度但还不够，继续打磨
- < 25%：核心价值定位有问题

**其他 PMF 信号**：

| 指标 | PMF 信号 | 不健康的信号 |
|------|---------|------------|
| 自然增长（Organic Growth） | > 50% 来自口碑 | 全靠付费获客 |
| 留存率 | 月留存 > 80% | 月留存 < 50% |
| 付费转化 | 7天内开始付费 | 90天以上才付费 |
| 使用频率 | 日活/周活 > 50% | 周活/月活 < 20% |
| NPS（净推荐值） | > 40 | < 0 |

### 3.3 PMF 验证的实践步骤

**四步验证法**：

```python
def pmf_verification_steps():
    """
    PMF 验证的四个步骤
    """
    steps = {
        "Step 1: 定义理想用户画像 (ICP)": {
            "问题": "你的产品最为了解决谁的问题？",
            "方法": "调研目标用户的特征，不是所有人都适合",
            "输出": "3-5 个用户画像标签"
        },
        "Step 2: 找到早期用户": {
            "问题": "谁有最痛的痛点？",
            "方法": "手动找——在论坛、社群、朋友圈问",
            "输出": "100-200 位早期测试用户"
        },
        "Step 3: 测量核心行为": {
            "问题": "什么行为说明用户获得了价值？",
            "方法": "定义 Aha Moment（啊哈时刻），即用户第一次说"这太棒了"的时刻",
            "输出": "关键行为指标（Activation Event）"
        },
        "Step 4: 留存测试": {
            "问题": "用户是否会回头？",
            "方法": "不要看下载量/注册量，看 D7/D30 留存",
            "输出": "留存率曲线"
        }
    }
    return steps
```

### 3.4 案例：Slack 的 PMF 验证

Slack 的前身是游戏公司 Tiny Speck 的内部沟通工具——游戏失败后，团队发现内部工具的价值。

**Slack 的 PMF 验证过程**：

| 阶段 | 行动 | 发现 |
|------|------|------|
| 内部使用 | 团队自己用，每天发 1000+ 条消息 | 团队协作效率提升 30%+ |
| 朋友内测 | 给 10 个朋友公司免费试用 | 所有人都说 "太棒了" |
| 邀请制开放 | 限时开放注册 | 2 周内 8000 个团队注册 |
| 留存验证 | 看 D30 留存率 | 93%——PMF 确认！|

**关键转折**：Slack 发现即使用户数没爆炸增长，但留下来的用户**日均使用时长 > 90 分钟**。这说明产品解决了真实的、高频的需求。

**Slack 的 Aha Moment**：一个团队在 Slack 上发送超过 2000 条消息后，这个团队基本不会离开。

### 3.5 案例：Notion 的 PMF 进化

Notion 从工具到平台的 PMF 路径很值得借鉴：

**阶段1：笔记工具**（2016）
- 用户画像：个人知识管理爱好者
- 留存：月留存 < 30%
- 问题：笔记市场竞争激烈，差异化不够

**阶段2：团队协作工具**（2018-2019）
- 用户画像：小团队、创业公司
- 痛点：需要同时管理 Projects + Docs + Wiki
- PMF 信号：月留存从 30% → 65%
- 关键决策：放弃个人市场，all-in 小团队协作

**阶段3：All-in-One Workspace**（2020+）
- 用户画像：远程团队、创作者
- PMF 确认：年收入增长率 400%+
- 护城河：用户的数据库、文档、模板都沉淀在 Notion 里

**教训**：PMF 不是一次就找到的。Notion 花了 3 年才找到真正的产品市场匹配。

## 四、Growth Loops——让产品自己增长

### 4.1 什么是 Growth Loop？

**Growth Loop（增长飞轮/回路）**：一个用户行为可以引发下一个用户增长的闭环。

**关键区别**：
- 传统漏斗：用户 → 注册 → 付费 （线性，单向）
- Growth Loop：用户 → 行为 → 带来新用户 → 新用户也做同样的事 （循环，自驱动）

### 4.2 四种核心 Growth Loops

#### Loop 1：病毒式增长循环

```
现有用户 → 邀请朋友 → 朋友注册 → 新产品免费使用 → 朋友也邀请 → ...
```

| 产品 | 病毒机制 | 效果 |
|------|---------|------|
| Dropbox | 邀请朋友获得 500MB 空间 | 2 个月增长 3900% |
| WhatsApp | 通讯录自动触发邀请 | 免费短信，用户自发传播 |
| Zoom | 会议链接天然需要共享 | 疫情期间 3 个月 20 倍增长 |

**病毒系数（K-factor）**：
$$K = \text{每个用户邀请人数} \times \text{邀请转化率}$$

- K > 1：病毒增长（每个用户带来多于 1 个新用户）
- K < 1：需要外部获客补充

**案例：Dropbox 的增长飞轮**
```
用户获得 500MB 空间 → 更愿意上传文件 → 体验更好 
→ 积极邀请朋友 → 朋友注册 → 空间再次增加 → ...
```

#### Loop 2：内容循环

```
用户 → 产生内容 → 内容被其他用户看到 → 其他用户也产生内容 → ...
```

| 平台 | 内容类型 | 循环机制 |
|------|---------|---------|
| YouTube | 视频 | 用户观看 → 发现好视频 → 订阅创作者 → 创作者上传更多 |
| 小红书 | 笔记 | 阅读 → 收藏 → 被激励也写 → 更多人看 |
| GitHub | 代码 | Fork → Star → 贡献 → 更多人看到你的项目 |

#### Loop 3：付费循环

```
用户在平台上花钱 → 拿到更好的结果 → 愿意花更多钱 → ...
```

| 平台 | 付费触发 | 循环 |
|------|---------|------|
| TikTok | 投 Dou+增粉 | 粉丝多了流量更多 → 更有动力投更多 |
| Airbnb | 更多房源 → 更多订单 | 收益好 → 上新更多房源 → 更好排名 |
| 亚马逊 | Prime 会员 → 更快配送 | 配送体验好 → 更多购物 → 续费 Prime |

#### Loop 4：数据网络效应循环

参考课时 5 的数据网络效应，这在 AI 时代尤为关键：

```
用户使用 AI 产品 → 产生标注数据 → 模型优化 → 用户体验提升 → 更多用户 → ...
```

### 4.3 案例：Notion 的增长飞轮

Notion 的 Growth Loop 非常精妙：

```
用户用 Notion 创建模板 → 分享到 Reddit 或 Twitter → 
其他人看到模板 → 注册 Notion 使用模板 → 
注册用户也创建自己的模板 → 更多模板 → 更多人注册
```

**量化效果**：
- 一个高赞"阅读清单"模板帖子：50 万阅读 → 2 万注册
- Notion 在 Reddit r/productivity 的成功故事：一个帖子带来 5000+ 注册
- 用户自发创建的模板总数：100万+

**关键基础设施**：
- 模板分享功能（一键复制模板）
- 社区模板市场
- 开放 API（可以构建公开的 Notion 工具）

## 五、OKR/KPI 树——从战略到执行的桥梁

### 5.1 OKR vs KPI

| 维度 | OKR（目标和关键结果） | KPI（关键绩效指标） |
|------|--------------------|------------------|
| 用途 | 设定目标、对齐方向 | 衡量执行、监控健康 |
| 频率 | 季度 | 持续/日常 |
| 弹性 | 有挑战性（70%完成就是好的） | 必须完成 |
| 关联性 | 上下对齐、层层连接 | 独立、看结果 |

### 5.2 从北极星指标拆解到 KPI 树

**北极星 → 一级指标 → 二级指标 → 三级动作**：

```
北极星：周活跃用户数

├─ 一级：新增用户数
│   ├─ 二级：渠道曝光量
│   │   └─ 三级动作：广告预算分配、素材制作量
│   └─ 二级：注册转化率
│       └─ 三级动作：落地页 A/B 测试、注册流程优化
│
├─ 一级：用户留存率
│   ├─ 二级：新用户 D7 留存
│   │   └─ 三级动作：激活引导流程、第一个 Aha Moment 优化
│   └─ 二级：老用户 D30 留存
│       └─ 三级动作：触达频率、内容个性化
│
├─ 一级：核心功能使用率
│   ├─ 二级：核心功能渗透率
│   │   └─ 三级动作：新功能引导、功能入口可见性
│   └─ 二级：使用频次
│       └─ 三级动作：推送策略、习惯养成设计
│
└─ 一级：付费转化率
    ├─ 二级：免费 → 付费的转化节点
    └─ 三级动作：付费点设计、定价策略
```

### 5.3 技术人的 OKR 编写

**技术部门 OKR 常见坑**：

| 错误写法 | 问题 | 正确写法 |
|---------|------|---------|
| "升级数据库到 Postgres 14" | 这是工程任务，不是 OKR | "将核心 API 的 P99 延迟从 500ms 降到 100ms" |
| "写 100 个单元测试" | 动作而非结果 | "将线上 bug 率降低 50%" |
| "重构用户模块" | 技术驱动而非业务驱动 | "提升用户注册流程的成功率从 60% 到 85%" |

**好的技术 OKR 必须有用户价值或业务价值的关联**。

### 5.4 案例：Airbnb 的 KPI 树

```
核心指标：预订过夜数 (Nights Booked)

├─ 新增房源数
│   ├─ 房东注册数
│   └─ 房源上架率（注册后上架的比例）
│
├─ 房源预订率
│   ├─ 搜索结果→浏览详情转化率
│   ├─ 浏览→收藏转化率
│   ├─ 收藏→咨询转化率
│   └─ 咨询→下单转化率
│
├─ 用户满意度
│   ├─ 入住体验评分
│   └─ 房东服务评分
│
└─ 复购率
    ├─ 都市区→旅游区的用户
    └─ 第一次体验后的 3 个月内又预订的比例
```

## 六、决策框架——如何在不确定性中做出选择

### 6.1 产品决策的核心困境

产品决策的本质是：**在信息不完备的情况下，做出不可逆的选择**。

技术人面对产品决策时常犯的错误：
- 过度追求"确定性"：等所有数据都确认了再改，已经晚了
- 过度依赖"直觉"：不做验证，拍脑袋做功能
- 过度分析"完美方案"：在 A/B 体验之间纠结一周，不如做一个小实验

### 6.2 六个实用的决策框架

#### 框架1：RIE（Risks, Impact, Effort）

```
对所有方案从三个维度打分（1-5分）：
- 风险（Risks）：技术风险、执行风险
- 影响（Impact）：对用户价值、商业价值
- 成本（Effort）：人月、资源

优先选择：Impact / (Effort × Risk) 最大的方案
```

**案例**：三个功能优先级判断

| 功能 | Impact | Effort | Risk | 得分 | 优先级 |
|------|--------|--------|------|------|-------|
| 搜索优化 | 5 | 2 | 2 | 5/(2×2)=1.25 | 1 |
| 社交分享 | 3 | 3 | 4 | 3/(3×4)=0.25 | 3 |
| 夜间模式 | 2 | 1 | 1 | 2/(1×1)=2.0 | 优先 |

#### 框架2：RICE（Reach, Impact, Confidence, Effort）

Intercom 公司的经典框架，在 RIE 基础上增加了「覆盖度」和「信心指数」。

```python
def rice_prioritization(features):
    """
    RICE 优先级评分
    features: 包含每个功能的 Reach, Impact, Confidence, Effort 字典
    """
    for name, data in features.items():
        rice_score = (data['Reach'] * data['Impact'] * data['Confidence']) / data['Effort']
        print(f"{name}: RICE = {rice_score:.1f}")
    
    return sorted(features.items(), 
                  key=lambda x: (x[1]['Reach'] * x[1]['Impact'] * x[1]['Confidence']) / x[1]['Effort'],
                  reverse=True)

features = {
    'AI 自动回复': {'Reach': 8, 'Impact': 9, 'Confidence': 3, 'Effort': 10},
    '批量导出':    {'Reach': 5, 'Impact': 6, 'Confidence': 5, 'Effort': 3},
    'API 集成':    {'Reach': 9, 'Impact': 8, 'Confidence': 4, 'Effort': 8},
}
# AI 自动回复: 8×9×3/10=21.6
# 批量导出: 5×6×5/3=50.0  ← 最高优先级！
# API 集成: 9×8×4/8=36.0
```

#### 框架3：ICE（Impact, Confidence, Ease）

Sean Ellis 的增长黑客框架，适合快速验证创意。

#### 框架4：决策树分析

适合有大量不确定性的复杂决策，为每个分支赋予概率和收益。

```
决策：是否开发 AI 推荐功能？
├─ 用户增长 20% (概率 40%) → 收入增加 ¥500万
├─ 用户增长 10% (概率 40%) → 收入增加 ¥200万
└─ 用户无变化 (概率 20%) → 收入增加 ¥0

期望值 = 0.4×500 + 0.4×200 + 0.2×0 = ¥280万
开发成本 = ¥100万
期望 ROI = (280-100)/100 = 180% → 值得做
```

#### 框架5：Opportunity Cost 评估

做一件事的代价不是它的成本，而是**不做另一件事的损失**。

**案例**：团队 3 个月时间，做 A 还是 B？

```
做 A 的收益：¥50 万/月
做 B 的收益：¥80 万/月
→ 做 A 的机会成本 = 不做 B 的损失 = ¥80 万/月
→ 显然应该做 B
```

#### 框架6：Inversion（逆向思考）

不是问"怎么成功"，而是问"怎么做会失败"。

```
问：「我们要怎么做才能让这个产品一年后死掉？」
答：定价太高、功能太复杂、不管用户反馈

→ 检查我们的策略：是否在定价、复杂度、用户反馈上踩了这些坑？
```

### 6.3 案例：Slack 的产品决策

**决策场景**：Slack 早期，是否要增加"项目管理"功能？

**团队分析**：
- 项目管理的用户需求确实存在 → Reach 高
- 但团队精力有限，做了项目管理意味着慢下来 → Effort 高
- Slack 的核心 JTBD 是"沟通"，项目管理是"跟踪" → 核心不匹配

**决策结果**：不做项目管理功能。让 Slack 专注于**消息和文件**，对方集成（Asana、Trello）去解决项目管理。

**结果验证**：专注策略让 Slack 在产品上极其专注，体验远胜于"什么都能做但什么都一般"的竞品。

## 七、案例深度解析

### 7.1 Superhuman——极致 JTBD 驱动的产品

Superhuman ¥210/月的定价让大多数人不理解。但理解 JTBD 后，这种定价逻辑就很清晰：

**用户群**：商务人士、高管、VC
- 这些人每天收 200-500 封邮件
- 每封邮件多花 10 秒 = 每年多花 90 小时
- 他们时薪 ¥500+ 
- 节省 90 小时 = ¥45,000 价值
- 年费 ¥2,520 → ROI = 45000/2520 = 17.8x

**Superhuman 的 PMF 验证**：
- 创始人自己做产品测试
- 从 100 位朋友内测，找到极致性能的体验
- 邀请制 + 等待名单制造稀缺感
- D30 留存率 > 95%（邮箱替代品的天花板）

**产品决策**：
| 选择 | Superhuman 的做法 | 其他竞品的做法 |
|------|-----------------|--------------|
| 定价 | ¥210/月 | 免费或 ¥30/月 |
| 目标用户 | 商务重度用户 | 所有人 |
| 功能 | 极致邮件处理 | 什么都有（日历+任务+笔记） |
| 增长 | 口碑 + 邀请码 | 广告投放 |

### 7.2 Notion——从危险边缘到 PMF 的转型

Notion 的创业故事是产品决策的教科书：

**2015-2016：错误的方向**
- 做全功能数据库 + 笔记（太复杂）
- 用户几乎没留存
- 融资困难，即将倒闭

**2017：关键决策——聚焦**
- 砍掉大部分功能
- 只做 Blocks + Templates
- 目标用户从"所有人"变成"小团队"

**2018-2019：PMF 找到**
- 模板分享 → 病毒式增长
- 小团队协作需求爆发
- 收入 2 年内增长 100 倍

**技术决策的启示**：
- 不是功能越多越好，**少即是多**
- 早期产品不要试图满足所有需求
- 用户画像越精准，产品决策越简单

## 八、总结

| 概念 | 一句话理解 | 实践建议 |
|------|-----------|---------|
| JTBD | 用户雇佣产品完成一个"任务" | 每次需求评审问"用户的真实 Job 是什么？" |
| PMF | 产品价值 > 用户获得成本 | 用 Sean Ellis 测试量化验证 |
| Growth Loop | 用户行为引发更多用户 | 找到产品的天然传播机制 |
| OKR/KPI 树 | 从愿景拆解到执行动作 | 北极星 → 一级指标 → 二级 → 动作 |
| 决策框架 | 在不确定性中做选择 | 任何决策用 RICE/ICE 打分 |

**技术人的行动清单**：

3. 找到你的产品中现有的或潜在的 Growth Loop
4. 下次做产品决策时，用 RICE 打分——把它变成一个习惯
