# 第1课：QUIC基础

> 参考 RFC 9000（QUIC Transport）、RFC 9001（TLS 1.3）、RFC 9114（HTTP/3）
> IETF QUIC Working Group, 2021-05 发布，RFC 9369（QUIC v2）2023-12 发布

---

## 1.1 为什么需要QUIC？TCP的痛点

### 队头阻塞（Head-of-Line Blocking, HoL）

TCP 虽然为上层提供可靠的字节流，但**一个丢失的包会阻塞其后所有已到达的数据**，直到重传完成。这是由 TCP 的有序交付特性决定的：

```
TCP 连接（单一字节流）
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ P1 │ P2 │ P3 │ P4 │ P5 │ P6 │ P7 │ P8 │
└──┬─┴──┬─┴──┬─┴──┬─┴──┬─┴──┬─┴──┬─┴──┬─┘
   │    │    │    │    │    │    │    │
   v    v    v    v    v    v    v    v
[OK]  [OK] [LOST] [OK] [OK]  ...（必须等P3重传）
```

在 HTTP/2 中，这种 HoL 问题更加严重——**HTTP/2 的流复用发生在 TCP 之上**。虽然 HTTP/2 允许多个流并行，但 TCP 层只有一个字节流。一旦某个 TCP 包丢失，所有 HTTP/2 流都会阻塞等待重传：

```
HTTP/2 多路复用（在 TCP 之上）
┌───────Stream 1────────┐
│  GET /page1.html      │ ← 等待
├───────────────────────┤
│  GET /api/data.json   │ ← 被阻塞！
├───────────────────────┤
│  POST /submit         │ ← 被阻塞！
└───────TCP Socket──────┘
    ↑ 一个丢包阻塞所有流
```

**HTTP/2 的 HoL 阻塞**论文证明：在 2% 丢包率下，HTTP/2 性能可能降至 HTTP/1.1 水平甚至更低。

### 连接延迟

TCP 三次握手 + TLS 1.3 需要 **2-RTT**（如果首次连接）：
```
Client                      Server
  │                           │
  │──────SYN─────────────────→│  (1) TCP 握手 - RTT 1
  │←────SYN-ACK──────────────│
  │──────ACK───────┐         │
  │                │         │
  │──────ClientHello────────→│  (2) TLS 1.3 - RTT 2
  │←────ServerHello+Finished─│
  │──────Finished───────────→│
  │                           │
  │←════HTTP Response═══════→│  终于可以传数据！
```

对于**短连接**（如 API 调用、小文件下载），握手延迟占主导地位。一个 RTT=100ms 的链路，仅握手就需 200ms。

### 其他 TCP 痛点

| 问题 | 说明 |
|------|------|
| 重传歧义 | TCP 无法区分"原始包的 ACK"和"重传包的 ACK" |
| 连接迁移困难 | IP/端口变化 = 连接断裂，移动网络极不友好 |
| 内核协议栈 | TCP 实现在操作系统内核中，更新迭代极慢 |
| 中间盒干扰 | NAT、防火墙等中间设备会修改/丢弃 TCP 包 |
| 头部开销 | TCP 头部至少 20 字节，选项更多 |

## 1.2 QUIC基于UDP的核心设计

QUIC 选择 UDP 而非 TCP 作为底层传输，核心原因：

1. **用户空间实现** — 可以在应用层快速迭代，无需升级内核
2. **避免中间盒干扰** — UDP 通常不被深度检查
3. **灵活性** — 加密、重传、拥塞控制都由应用层控制

```
OSI 模型对比：

TCP/TLS 栈：
┌──────────────┐
│   HTTP/2     │
├──────────────┤
│   TLS 1.3    │
├──────────────┤
│   TCP        │ ← 内核态
├──────────────┤
│   IP         │
└──────────────┘

QUIC 栈：
┌──────────────┐
│   HTTP/3     │
├──────────────┤
│   QUIC       │ ← 用户态（包含TLS 1.3 + 传输层）
├──────────────┤
│   UDP        │ ← 内核态
├──────────────┤
│   IP         │
└──────────────┘
```

### QUIC 的核心设计原则

1. **内置 TLS 1.3** — 不是"TLS over QUIC"，而是 TLS 1.3 握手直接输出 QUIC 的加密密钥和传输参数
2. **多路复用无 HoL** — 多流完全独立，一个流的丢包不影响其他流
3. **连接迁移** — 通过 Connection ID 标识连接，IP 变化无需重连
4. **0-RTT 建连** — 向已通信过的服务器发送数据只需 0-RTT
5. **前向纠错可用** — 协议设计预留了 FEC 空间

## 1.3 连接建立：1-RTT vs 0-RTT

### 首次连接（1-RTT）

QUIC 首次连接只需 **1 个 RTT** 即可开始传输数据（比 TCP+TLS 的 2-RTT 少一半）：

```
Client                              Server
  │                                   │
  │───Initial (CRYPTO Frame:         │
  │   ClientHello)                  →│
  │                                   │
  │←──Initial + Handshake            │
  │   (CRYPTO Frame: ServerHello,    │
  │   证书, Finished)                │
  │                                   │
  │───Handshake (CRYPTO Frame:       │
  │   Finished) + 1-RTT Data        →│  ← 此时已可发数据！
  │                                   │
  │←──1-RTT Data (HTTP Response)    ←│
```

关键点：**QUIC 的握手和传输参数协商在同一个 RTT 内完成**，因为 TLS 1.3 内建在 QUIC 中。

### 0-RTT 连接（非首次连接）

对于之前连接过的服务器，客户端可以**在第一个包中就携带应用数据**：

```
Client                              Server
  │                                   │
  │───Initial + 0-RTT Data ─────────→│  ← 立即发送请求数据
  │   (包含缓存的会话票据)           │
  │                                   │
  │←──Initial + Handshake +          │
  │   1-RTT Response                ←│
```

0-RTT 的工作原理：
- 客户端缓存服务器的 `NEW_TOKEN` 帧和会话票据
- 使用 PSK（Pre-Shared Key）模式恢复会话
- 0-RTT 数据有**重放攻击**风险（见第3课）

**对比**：

| 场景 | TCP+TLS 1.3 | QUIC |
|------|-------------|------|
| 首次连接 | 2-RTT | 1-RTT |
| 重连（有会话缓存） | 1-RTT | 0-RTT |
| 连接迁移 | 需重建连接 | 0ms (Connection ID) |

## 1.4 与HTTP/2的对比

| 特性 | HTTP/2 | HTTP/3 (QUIC) |
|------|--------|---------------|
| 传输层 | TCP | QUIC (UDP) |
| 传输 HoL 阻塞 | ❌ 有 | ✅ 无 |
| 流独立性 | 受TCP HoL影响 | 完全独立 |
| 连接建立 | TCP+TLS >= 1-RTT | QUIC 0/1-RTT |
| 头部压缩 | HPACK (依赖有序传输) | QPACK (适应无序) |
| 连接迁移 | 需重建 | 天然支持 |
| 实现位置 | 内核TCP + 用户空间 | 全部用户空间 |
| 推送功能 | 支持 | 支持（设计更简单） |
| 协议演进 | 困难（受内核/中间盒限制） | 容易（应用层） |

### 一个形象的类比

> **HTTP/2** 就像一条单车道高速公路——多辆车（流）共享一条路，一辆车抛锚（丢包），后面所有车都得停。  
> **HTTP/3** 就像多条独立的车道——每条车道上的车互不影响，一辆车抛锚只影响它自己的车道。

---

## 一句话总结

QUIC 是基于 UDP 的传输协议，内置 TLS 1.3，通过流独立性和 0/1-RTT 建连解决了 TCP 的队头阻塞和连接延迟问题，HTTP/3 是基于 QUIC 的 HTTP 语义映射。
