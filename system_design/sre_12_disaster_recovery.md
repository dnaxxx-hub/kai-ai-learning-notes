# 容灾与备份 — RPO/RTO / 备份策略 / 异地多活 / 故障切换 / 演练

## 一、RPO / RTO 定义

### 核心指标
```
RPO (Recovery Point Objective) —— 数据丢失容忍度
    上一次备份 → 故障 → 数据丢失
    |<---   RPO   --->|
    越小越好，成本越高

RTO (Recovery Time Objective) —— 服务恢复时间
    故障 → 恢复 → 可用
    |<---   RTO   --->|
    越小越好，复杂度越高
```

### 常见等级
| 等级 | RPO | RTO | 方案 | 典型业务 |
|------|-----|-----|------|----------|
| L0 | 0 | 秒级 | 异地多活 | 金融交易 |
| L1 | 秒级 | 分钟级 | 同城双活 | 支付系统 |
| L2 | 分钟级 | 分钟级 | 主备切换 | 核心业务 |
| L3 | 小时级 | 小时级 | 冷备恢复 | 非核心业务 |
| L4 | 天级 | 天级 | 异地归档 | 日志/报表 |

## 二、备份策略

### 备份类型
| 备份类型 | 描述 | 恢复速度 | 存储空间 | 频率 |
|----------|------|----------|----------|------|
| **全量（Full）** | 全部数据 | 最快 | 最大 | 低（每周） |
| **增量（Incremental）** | 上次备份后的变化 | 慢（需全量+所有增量） | 最小 | 高（每小时） |
| **差异（Differential）** | 上次全量后的变化 | 中（需全量+最近差异） | 中 | 中（每日） |
| **日志（Log）** | 事务日志 | 可恢复到任意时间点 | 按需 | 连续 |

### 3-2-1 原则
- **3**：至少保留 3 份副本
- **2**：使用 2 种不同的存储介质
- **1**：至少 1 份异地存放

### 备份验证
- **定期恢复测试**：每月至少跑一次完整恢复演练
- **checksum 校验**：备份完整性验证
- **监控告警**：备份失败 → P1 告警

## 三、异地多活架构

### 同城双活（Metro Active-Active）
```
DC-A (主) ←—— 光纤同步复制 ——→ DC-B (主)
同一城市，距离 < 100km
```
- **优点**：RPO ≈ 0，延迟低
- **缺点**：同城单点（自然灾害覆盖）
- **典型**：金融行业两地三中心中的同城部分

### 两地三中心
```
城市1 ─── 同城双活 ─── 数据中心A / 数据中心B
城市2 ─── 异地灾备 ─── 数据中心C（冷备/温备）
```
- **特点**：兼顾同城高可用 + 异地容灾
- **核心**：数据从 A/B 异步复制到 C

### 异地多活（Geo-Distributed Active-Active）
```
Region-A (杭州) ←—— 异步复制 ———→ Region-B (上海)
Region-C (北京) ←—— 异步复制 ———→ Region-D (广州)
```
- **要求**：业务单元化（Unit Architecture），用户请求路由到最近机房
- **挑战**：数据冲突、跨域延迟、Session 同步
- **典型案例**：Google Spanner、阿里集团单元化

### 架构选型
| 方案 | RPO | RTO | 成本 | 复杂度 |
|------|-----|-----|------|--------|
| 冷备 | 天级 | 天级 | 低 | 低 |
| 主备 | 分钟-小时 | 分钟级 | 中 | 中 |
| 同城双活 | ~0 | 秒级 | 高 | 中高 |
| 两地三中心 | 分钟级 | 分钟级 | 很高 | 高 |
| 异地多活 | 秒级 | 秒级 | 极高 | 极高 |

## 四、故障切换（Failover）

### 切换模式
- **主动切换（Planned）**：计划内维护，可在低峰期操作
- **被动切换（Unplanned）**：故障触发，需要自动化 + 人工确认
- **灰度切换**：逐步切流量，先 1% → 10% → 100%

### DNS 切换
```
故障检测 → 修改 DNS 记录 → TTL 等待 → 生效
TTL 设置：60s-300s（越短切换越快，但 DNS 查询压力越大）
```

### 负载均衡切换
- **Global Server Load Balancer (GSLB)**：跨区域流量调度
- **健康检查**：HTTP/TCP 探活，异常自动摘除
- **权重分配**：按机房容量分配流量比例

### 关键检查清单
- [ ] 数据一致性确认（Replication Lag、数据校验）
- [ ] 资源容量确认（目标机房是否扛得住双倍流量）
- [ ] 依赖服务确认（数据库、缓存、消息队列是否已切）
- [ ] 回滚方案（切失败了怎么回来）

## 五、恢复演练

### Plan-Drill-GameDay 递进模式

| 阶段 | 频率 | 内容 | 参与者 |
|------|------|------|--------|
| **Plan** | 季度 | 制定故障预案（Runbook） | SRE |
| **Drill** | 月度 | 内部演练（受控环境） | SRE + 开发 |
| **GameDay** | 半年度 | 全链路故障模拟（生产/预发） | 全团队 |

### GameDay 标准流程
```
1. 提前宣布：什么时间、什么范围（不告知具体故障类型）
2. 定义成功标准：RPO < 5min, RTO < 15min
3. 注入故障：通过混沌工程平台自动注入
4. On-call 响应：观察实际的告警→响应→恢复过程
5. 复盘：5 Whys 分析，改进 Runbook
6. 行动项：落实到具体责任人 + 时间节点
```

### 常见失败原因
- Runbook 过时（IP/密码/机器已变更）
- 数据库复制延迟超出预期
- DNS TTL 过长导致流量切换慢
- 忘了通知相关业务方
