# AI Agent 工程 #1 — Agent 架构基础

> 学习笔记 | 2026-02-27

---

## 1. AI Agent 定义

**AI Agent** 是一个能自主感知环境、基于目标进行推理决策、并采取行动以实现目标的智能系统。

### 与普通 LLM 调用的区别

| 维度 | 普通 LLM 调用 | AI Agent |
|------|--------------|----------|
| 流程 | 单次问答 | 多轮循环，持续交互 |
| 状态 | 无状态 / 单次上下文 | 有状态，维护对话历史 |
| 工具 | 无 | 可调用外部工具 |
| 目标 | 回答当前问题 | 达成既定目标 |
| 自主性 | 完全被动 | 部分或完全自主推理 |

**一句话总结：** LLM 是大脑，Agent 是大脑 + 手 + 眼 + 反馈神经回路。

---

## 2. Agent 核心循环

所有 Agent 架构都遵循一个基本循环：

```
                     ┌─────────────┐
                     │   感知       │  ← 接收输入（用户消息、环境状态、工具返回）
                     │ (Perceive)  │
                     └──────┬──────┘
                            ▼
                     ┌─────────────┐
                     │   思考       │  ← LLM 推理（分析当前状态、决定下一步）
                     │  (Think)    │
                     └──────┬──────┘
                            ▼
                     ┌─────────────┐
                     │   行动       │  ← 执行动作（回复用户、调用工具、修改状态）
                     │  (Act)      │
                     └──────┬──────┘
                            ▼
                     ┌─────────────┐
                     │   观察       │  ← 评估结果（工具返回值、环境反馈）
                     │ (Observe)   │
                     └──────┬──────┘
                            │
                            └──→ 循环（直到目标达成或终止条件触发）
```

这个循环的**关键属性**：
- **持续性**：Agent 不会在一次响应后就结束，而是持续迭代
- **反馈驱动**：每次行动的结果都会影响下一次的思考
- **条件终止**：达到目标、超出限制、人工介入等条件下终止

## 3. ReAct 模式（Reasoning + Acting）

ReAct = **Rea**soning + **Act**ing，由 Yao et al. 2022 提出。

### 核心思想

将**思维链（Chain-of-Thought, CoT）**与**工具调用**交替进行——每一步先思考说什么/做什么，然后执行，观察结果，继续思考。

### 典型流程

```
问题: "北京和上海哪个更远？"

思考1: 我需要查到北京和上海的坐标，计算距离。
动作1: search("北京 经纬度")
观察1: (39.9042° N, 116.4074° E)

思考2: 拿到了北京的坐标，接下来查上海的。
动作2: search("上海 经纬度")
观察2: (31.2304° N, 121.4737° E)

思考3: 两地坐标已知，用距离公式计算...
动作3: calculate("haversine(39.9,116.4,31.2,121.5)")
观察3: ≈1067 km

思考4: 北京到上海大约1067公里。
最终回答: 北京到上海的直线距离约1067公里。
```

### ReAct 的优势
- **可解释性强**：每一步思考可见，调试方便
- **减少幻觉**：通过工具验证中间结论
- **灵活应对**：每个步骤基于当前实际结果，而不是预设路径

### ReAct 的局限
- Token 消耗大（思考过程也占上下文）
- 简单任务没必要（杀鸡用牛刀）
- 容易陷入思考-行动-观察的死循环

## 4. Plan-and-Execute 模式

### 核心理念：先规划，再执行

```
任务: "帮我写一篇关于Agent架构的文章并保存到文件"

[规划阶段]
1. 确定文章大纲
2. 为每个章节搜集资料
3. 依次撰写各章节
4. 保存到文件

[执行阶段]
动作1: think("制定文章大纲")
→ 输出大纲

动作2: search("Agent架构 ReAct Plan-and-Execute")
→ 获取参考资料

动作3: think("撰写第一章")
→ 输出第一章内容

...后续步骤依次执行...
```

### 与 ReAct 的对比

| 维度 | ReAct | Plan-and-Execute |
|------|-------|-----------------|
| 规划时机 | 边做边想（每一步） | 先规划后执行 |
| 灵活性 | 高，可随时调整 | 较刚，但支持 re-plan |
| 复杂任务 | 容易迷失 | 更适合 |
| 简单任务 | 过度思考 | 规划成本高 |
| 典型场景 | 问答、推理类 | 多步骤工作流 |

### 混合模式

实践中常用 ReAct 局部 + Plan-and-Execute 全局：
- 顶层：Plan-and-Execute 做任务分解
- 每个子任务：用 ReAct 模式执行

## 5. 关键组件

### 5.1 系统提示（System Prompt / Persona）

系统提示定义了 Agent 的"人格"和运行规则，好的系统提示包含：

```
你必须严格遵守以下规则：
1. 角色定义 — 你是谁、能做什么、不能做什么
2. 工具说明 — 每个工具的用途、参数、调用方式
3. 行为约束 — 什么时候调用工具、什么时候直接回复
4. 输出格式 — 结构化输出要求（JSON、Markdown等）
5. 安全边界 — 禁止操作、敏感内容处理
6. 目标导向 — 始终围绕用户目标，不要跑偏
```

**最佳实践：**
- 系统提示应**足够具体但不过度约束**
- 工具描述使用自然语言，让 LLM 理解意图而非格式
- 定期评估和更新系统提示（Prompt Engineering 是持续过程）

### 5.2 上下文窗口管理

LLM 的上下文窗口是有限的（4K-200K tokens），Agent 循环中容易填满。

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 滑动窗口 | 只保留最近 N 轮对话 | 实现简单 | 丢失历史 |
| 摘要压缩 | 将历史对话压缩成摘要 | 保留关键信息 | 可能丢失细节 |
| 结构化记忆 | 分桶存储（近期/长期/摘要） | 信息完整 | 实现复杂 |
| 检索增强 | 按需检索历史片段 | 灵活高效 | 依赖检索质量 |

**OpenClaw 实际做法参考：**
- 完整上下文 → LLM
- Agent 运行日志 → 文件存储（带时间戳）
- 关键决策 → 写入 memory 文件持久化

### 5.3 反馈循环（结果评估 → 自我修正）

Agent 不是一次就完美的——需要自我评估和修正。

```
动作执行 → 观察结果 → 评估结果
  ↑                        │
  │                    ┌────┴────┐
  │                  成功吗?   失败?
  │                    │         │
  │                  继续←─→尝试修复
  │                         │
  └────────── 重新执行 ──────┘
```

**评估维度：**
- 工具调用是否成功（返回值判断）
- 输出是否符合预期格式
- 目标是否达成（理解用户意图）
- 是否陷入循环（需要外部干预）

**自我修正策略：**
1. **重试** — 工具调用失败，修正参数后重试
2. **回退** — 当前路径不通，回到上一个决策点
3. **切换方法** — 换个思路解决问题
4. **请求帮助** — 向用户询问澄清

## 6. 框架比较（概念层面）

### 6.1 LangChain Agent vs 原生 Agent 循环

| 维度 | LangChain Agent | 原生 Agent 循环 |
|------|----------------|-----------------|
| 抽象层次 | 高层框架，封装了 Agent 循环 | 自己控制每个步骤 |
| 灵活性 | 受框架约束，修改需了解框架源码 | 完全可控 |
| 学习曲线 | 先学框架再学概念 | 先学概念，代码就是概念本身 |
| 依赖 | 强依赖框架版本 | 无外部依赖 |
| 调试 | 黑盒较多 | 完全透明 |
| 适用场景 | 快速原型、标准场景 | 定制化需求、深入理解 |

**观点：** 先用原生循环理解概念，再用框架提升效率。不要从框架入门。

### 6.2 工具注册模式

工具注册是 Agent 系统的核心连接点：

```
工具注册表（Tool Registry）
├── 工具名称（唯一标识）
├── 工具描述（LLM 理解用途）
├── 参数 schema
├── 执行函数（实际调用的代码）
└── 返回值处理
```

**两种注册方式：**

```python
# 方式一：装饰器注册（推荐，声明式）
@tool(description="计算两数之和", schema={"a": "int", "b": "int"})
def add(a, b):
    return a + b

# 方式二：手动注册（底层）
registry = ToolRegistry()
registry.register("add", add_func, description="...", schema=...)
```

**关键设计考量：**
- 工具描述的质量直接影响 LLM 是否能正确选择工具
- 参数 schema 需要精确且完整
- 错误处理：工具内部异常不应崩溃整个 Agent

### 6.3 状态管理

Agent 需要在循环中维护状态：

| 状态类型 | 内容 | 存储位置 |
|---------|------|---------|
| 会话状态 | 当前对话历史 | 内存（上下文窗口） |
| 持久状态 | 用户偏好、长期记忆 | 文件/数据库 |
| 运行状态 | 当前子任务进度 | 文件/变量 |
| 环境状态 | 工具可用性、权限 | 运行时 |

**状态管理原则：**
- 内存中的状态要轻量（否则占 Token）
- 持久化的状态要结构化（便于检索）
- 运行状态要支持快照与恢复（容错）

## 7. 工程考量

### 7.1 错误恢复

Agent 运行中可能出错的地方：

```
层    面         错误类型                恢复策略
───────  ─────────────────  ─────────────────────
LLM      JSON 解析失败       重试 + 严格提示
工具     网络超时             重试 + 指数退避
逻辑     陷入死循环           最大步数截断
状态     上下文溢出           摘要压缩
安全     越权操作             回滚 + 告警
```

**最大截断（Hard Stop）：**
```python
MAX_STEPS = 25  # 防止无限循环
step_count = 0
while not done and step_count < MAX_STEPS:
    step_count += 1
    # Agent 循环
```

### 7.2 超时处理

| 超时类型 | 建议值 | 说明 |
|---------|--------|------|
| LLM 推理 | 30-60s | 单次 LLM 调用 |
| 工具执行 | 10-30s | 外部 API 调用 |
| 总循环 | 5-10min | 整个 Agent 会话 |

### 7.3 重试策略

```
重试金字塔（Retry Pyramid）:
  
  Level 1: 立即重试    ← 瞬态错误（网络抖动）
  Level 2: 延迟重试    ← 限流、服务不稳定
  Level 3: 降级重试    ← 换工具 / 换模型 / 简化请求
  Level 4: 放弃        ← 最终错误，报告用户

  延迟公式: delay = min(base_delay * 2^attempt, max_delay)
  典型值: base_delay=1s, max_delay=30s
```

**重试重要原则：幂等性**
- 工具调用应该幂等（多次调用结果一致）
- 非幂等操作（如发送邮件）需要先确认再重试

## 8. 与我们系统的关联：OpenClaw 架构中的 Agent 循环

### OpenClaw 的 Agent 架构（简化）

```
 用户输入
    │
    ▼
┌─────────────┐
│  感知层      │  ← 理解用户意图、提取上下文
│ (Perceive)  │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  调度层      │  ← 路由到对应能力模块
│ (Schedule)  │     根据用户请求类型分发
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  引擎层      │  ← LLM 推理 + 工具调用
│ (Engine)    │     - 系统提示构建
│             │     - 工具注册表查询
│             │     - 上下文管理
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  存储层      │  ← 记忆持久化
│ (Storage)   │     - memory/ 目录
│             │     - TOOLS.md / AGENTS.md
│             │     - 每日日志
└─────────────┘
```

### 映射关系

| Agent 概念 | OpenClaw 实现 |
|-----------|--------------|
| 感知 (Perceive) | 用户消息解析、上下文注入、SOUL.md / USER.md 加载 |
| 思考 (Think) | LLM 推理引擎（带 system prompt + tools） |
| 行动 (Act) | 工具调用（read/write/exec/web_search/browser 等） |
| 观察 (Observe) | 工具返回值解析 → 下一次输入的上下文 |
| 工具注册 | tools 声明 + gateway 路由 |
| 状态管理 | 内存中的会话上下文 + 持久化的 memory 文件 |
| 反馈循环 | 多轮对话 + 自我修正指令（重试、回退） |
| 系统提示 | AGENTS.md / SOUL.md 加载为 system prompt |

### OpenClaw 的特色

1. **文件即记忆** — `memory/`, `MEMORY.md`, `AGENTS.md` 构成了 Agent 的持久化知识体系
2. **无状态 ⇄ 有状态** — 每次会话从文件重建上下文，运行中维护会话状态
3. **工具即能力** — 工具注册扩展 Agent 能力边界，Gateway 做安全路由
4. **外部交互桥接** — 日历、任务、多维表格等飞书生态打通，让 Agent 能操作真实世界

## 总结

```
Agent = LLM（大脑）+ Tools（手脚）+ Memory（记忆）+ Loop（循环）+
          Feedback（反馈）+ Error Handling（容错）
```

核心要点回顾：
1. **Agent ≠ LLM**，核心区别在于自主循环和目标驱动
2. **ReAct** 适合推理型任务（边想边做），**Plan-and-Execute** 适合复杂多步骤任务
3. **系统提示**是 Agent 行为的宪法，**上下文管理**是生命线，**反馈循环**保证质量
4. **工程化**要考虑错误恢复、超时、重试、幂等性
5. OpenClaw 本质就是一个 Agent 循环系统，理解其架构就是理解 Agent 本身
